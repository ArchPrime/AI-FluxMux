AI-FluxMux

What is AI-FluxMux?

AI-FluxMux is a router for OpenAI Compatible local and cloud-based AI models, that lets you switch quickly between them at will, based on which model can best handle your task at that moment — even mid chat, when switching between a hot cloud model and a local one. No manual endpoint re-configuration or script changes required.

AI-FluxMux is a model tweaker, where you can manually tune and optimise settings to address different goals and priorities, or use a priorities-based wizard to extract every drop of performance out of your model and hardware in line with those priorities: Stability, Speed, Fidelity, Context length, Reply length, Reasoning depth, and for cloud models, Token Cost Economy. Enabling vision (where the model supports it) reallocates resources automatically, while leaving no performance on the table.

AI-FluxMux is a laboratory where you can easily set up a library of models and settings variants, and compare their real-world behaviour, swapping quickly between them at will while working on real tasks. You can also benchmark how well one model profile hands off to another during a chat.

Setting up

1 Install AI-FluxMux

Unzip AI-FluxMux to a folder you own (for example C:\AI-FluxMux). Do not unzip into Program Files: Windows does not let AI-FluxMux update some of its own files there.

Double-click FluxMux.Avalonia.exe to launch. Windows may show SmartScreen because this build is not code-signed; choose More info, then Run anyway.

Your settings will live in %AppData%\AI-FluxMux\.

2 Install llama-server

You need to install llama-server on your local machine if you are going to run any local models, as this is what launches them.

·        You should choose a version optimised for your GPU. Get this from GitHub. Do not use the standard Windows installer from the main llama website — as of writing, this does not support GPU acceleration.

·        Look for the latest nightly build (b#####) on GitHub, here: https://github.com/ggml-org/llama.cpp/releases?q=b

·        Look in particular for the build that matches your CPU and GPU.

·        If you have an NVIDIA RTX GPU, download the Windows CUDA zip for the highest CUDA version your card's driver will run. Also download the matching CUDA DLLs zip listed beside it.

·        Ensure your NVIDIA RTX actually has the latest Game Ready or Studio driver installed (from NVIDIA), or they may not work. You do not need the CUDA developer toolkit.

·        Extract your downloaded zip file(s) all together into your preferred installation folder.

Remember to update llama-server every now and then. Check GitHub directly, or use the AI-FluxMux Environment tab → Check for updates. It only offers a newer zip of the same Windows CUDA / Vulkan / CPU family as the folder already in use, and it does not download or install it for you.

Installing that newer zip is the same manual job as above, with two things to watch.

·        Confirm the version you download is correct for this PC's GPU and Windows.

·        Do not mingle new and existing files. Extracting into a fresh folder is safest, because you can keep the old one until Launch works. If you would rather reuse the same folder, back it up, empty it completely, then extract the downloaded zip file(s) into it.

3 Establish Agent / Client app settings

·        Read the endpoint provider's installation guide, if you have not set up already.

·        You should start by opening the connection settings of your preferred Client app.

·        As the API Provider, use OpenAI Compatible.

·        As the base URL, use http://127.0.0.1:5001/v1. If you use Cline, omit the /v1 part — Cline adds it itself, and /v1/v1 will fail. You can use another port if you do not want to use 5001, but remember to use the same number in AI-FluxMux Endpoint settings.

·        As the OpenAI compatible key, type a single space.

·        As the Model ID, use local, in lower case. The Servers tab shows the live address and model id on its Model API line, so you can copy exactly what AI-FluxMux is offering.

·        Save the settings when you are done.

This first setup is the one part you always do by hand. From then on, AI-FluxMux keeps Cline and Harness in step with whatever model is loaded, so you do not go back into their settings each time you switch models.

Choosing a Client app for local models

AI-FluxMux does not replace your Client app, but rather acts between your Client, and the model server to manage GPU and VRAM, Images, Context and other settings every time you change and update models, and compaction of older forwarded turns. With routing on, it can also route to models that better fit the task. Your Client app still holds the full chat, whatever the models and AI-FluxMux are doing behind the scenes.

Your choice of Client app can still make a significant difference to how long chats can continue without losing focus or accuracy of recall, as well as to stability. Cline and DeepSeek Harness are the two tested with AI-FluxMux, and the two whose own settings it keeps in step with the loaded model. Any other OpenAI Compatible Client app should work, however, if pointed at the same Port.

Cline

Cline is an extension inside VS Code, and that mature ecosystem and huge extensions library offer a lot of benefits for coders. However it can also fill a local model Context quickly — especially with large rule files and many tools — and can reach a point where compaction cannot help, because a single turn can overfill the available Context. AI-FluxMux automatically manages your Cline Context, Images, and Compaction settings to suit the current model. See Cline for more details.

You should disable GPU acceleration in VS Code. This frees up a bit of space for your local models, and makes exiting and restarting Cline and VS Code much less flaky. Press Ctrl+Shift+P, run Preferences: Configure Runtime Arguments (that opens argv.json, not settings.json), set disable-hardware-acceleration to true, then File → Exit and start VS Code again. This should fix messages like Error loading webview or Could not register service worker that often pop up when restarting VS Code.

DeepSeek Harness

Harness is a separate program that communicates via its own web chat interface. Some people report that on local models, its context management is so good that it feels close to what they can get from cloud model chats. AI-FluxMux can launch a new Harness session from any active Quick Select slot, and in so doing automatically updates Harness to use whichever model Context and other settings best apply for that selection. Harness, as of writing, is working pretty well, but is a developer preview, so bugs and breaking changes are expected. It currently does not handle chat turn problems as resiliently as Cline. See DeepSeek Harness for more details.

Other OpenAI Compatible Client apps

So far, only Cline and Harness can have their own settings — available Context and so on — synchronized by AI-FluxMux to follow whatever model is loaded. Other clients still work, if pointed at the same Port, but you will need to manually change Context and related settings yourself and revisit them when you change models. To teach AI-FluxMux to write another client's settings file, see Appendix C — Endpoint adapters (JSON).

Starting a new chat

As a rule, routing from cloud to cloud, or between cloud and a hot local model, works well with either of the Client apps tested. With local-to-local model switches you typically get best results from launching a new chat each time you switch. Your old chat history is not lost, but your context starts clean each time. That said, local model switches may not be required as often, or at all, in Harness, due to the better context management.

You can jump between Client apps at will, leaving them all pointed at the same Port in AI-FluxMux. No scripts need to be edited by hand to cope with new models or endpoints, and settings in AI-FluxMux do not have to change from one Client app to the next. Close any running chats and start a new chat whenever you do switch, because the context the current model has built up will not otherwise match the chat history in the new app.

Choosing models

The best options seem to change daily. As of writing, when it comes to local models, Qwen 3.8 27B offers a good balance of size versus performance.

Lower quantisation levels within this are faster and smaller, but remain less faithful to the original task over long chats. For NVIDIA cards, NVFP4 versions (in .gguf format) can arguably offer the best performance and fidelity balance over long chats for most things, but use a bit more memory. Check current model reviews in relation to your GPU.

Managing Client apps and Context

·        Restrict each chat to one focused task.

·        Start a new chat whenever a Client app reports an error, switching models as required if the error is that the current model has run out of room. AI-FluxMux will try to intervene first to prevent most errors and offer you model options that seem more likely to succeed, whenever it detects a problem is likely under your current model — but you can equally manage this yourself once you have a sense of what model settings are best for a given scenario.

·        Retrying, or adding a different question to a current chat after an error has occurred, can sometimes work after a model change, but this becomes increasingly less likely the larger the current chat history or context is.

·        You can also try to narrow the scope of your question or task if you keep striking capacity limits with your local model options. Or you can temporarily switch to a cloud model for anything that proves too complex or resource intensive, then switch back once you hit more traditionally straightforward tasks, like coding.

·        You can of course shift entirely to OpenAI Compatible cloud models, switching at will between these, even between providers, based on whether frontier-level performance or cost is the most important factor to you in the current phase of work.

First-day path

Do these in AI-FluxMux, once you have llama-server and your chosen Client app set up. Work from tab to tab, in this order.

Servers tab

1.       Endpoint settings: set Port to the same number you set in your Client app (or vice-vera). Double check this. Do not set your AI-FluxMux Port to the port that Harness web UI uses — that is entirely separate. The Model API line will reflect the resulting address and model id exposed to your Client app. Don’t use a port where that port (or the next one up), is already used by an unrelated app.

2.       Local model server: browse to the folder where you keep the downloaded local model (.gguf) files you want AI-FluxMux to see. Any vision projector files for your models should be in that folder too — these also have the .gguf extension, but have mmproj somewhere in the name. Despite sharing that file extension, they are helpers, not models themselves.

3.       Local model server: pick your install from the llama-server installation list. AI-FluxMux scans for installs, so yours is usually already there; Browse to llama-server.exe only if it is not. Test Server Readiness then checks those paths without starting a model.

4.       Cloud provider: for every cloud AI account you have a subscription to, select the provider, paste in your associated API key or secret, hit Validate Cloud Key, then if validate succeeds, hit Save Key. Most providers are already in the list with their addresses filled in, so a key is all you need — see Cloud providers. A host that is not listed needs a Name and Base URL, then Add custom provider. Remove custom to delete.

Model Profiles tab

Pick a local model from the dropdown list (but not an mmproj file), then click Create new local model profile.

A Default model profile is created with settings that should be safe to run as-is, though they may not be fully optimised for your priorities. Rather than changing any settings in this profile, you should scroll to the bottom of the open profile, type a name, and click Make New Variant, then change settings there. You can still edit the default profile if you really need to, but first you need to click to unlock the associated padlock icon. Remember to lock it again afterwards.

For a cloud model, choose the Provider, then pick a Model id from the list. Refresh Models asks the provider what models it offers, or use Or paste id for anything not listed. Then click Create new cloud model profile. Similar advice applies as for local models. Note that Refresh Models can list model ids that chat will not actually accept (often due to OpenAI compatibility, or your subscription level), so if Validate fails, try another model.

For any newly created profile, click Validate to endpoint. That sends a short "reply ready" check, though not a long coding test. A green checkmark appears if successful. A validated model is then available for launching, if you want it, from a slot in the Quick Select tab. If you changed a cloud Provider or Model id, click Save profile first before validating.

A failure to validate means the basic conditions for successful operation are absent. You probably need to choose another model, or different model settings, or to sort out a problem with your cloud subscription, or with local VRAM availability, or similar. The warning triangle stays on that profile row and a short reason appears in the status line under the profile. A failure to validate with a default model profile is the main reason you might want to unlock it. When unlocked you can delete the profile, or try changing its settings.

The other buttons in an open profile are Save profile, Revert changes (drop unsaved edits), Use model defaults (load the starting settings as unsaved edits), Rename, and Delete. Note that Deleting a default model profile removes that model profile and all its variants from AI-FluxMux after a confirmation; though it does not delete the source model file (.gguf) from disk.

Quick Select tab

1.       Choose whether you want to use Route requests. Probably leave it off while you are still setting up models and testing your connections — come back to it later, once you have enough models set up that routing between them makes sense. That is, once you have a range of local and optionally cloud model profiles with different strengths and weaknesses: for example one with the largest Context your GPU can handle, one with vision but a smaller Context, one with larger max tokens for longer answers, one with higher temperature for more creativity and variability but less stability, and so on.

2.       Hit Add New Slot. Choose one of your validated profiles in the Validated profile list, then click Save to keep that model in that new slot. You cannot add another slot while a populated slot is still unsaved.

3.       Hit Launch. Wait until the slot shows it is ready. Then send the first message to the running model from your Client app.

Each slot also has Restart, Stop, and Delete Slot. Only one local model is ever loaded at a time, so launching a second local model stops the first. When a local and a cloud model are both launched, the one that is not currently answering shows Hot — standing by; you may also see Hot — starting or Hot — fault. A second local slot never shows those, because it is not loaded.

Route requests

Tick Route requests once you are ready to try routing. Pop up routing prompts can be switched on with it (recommended), so any routing decision required of you appears in a small window on top of your current application instead of staying hidden behind it. The same buttons appear in the Diagnostics panel of AI-FluxMux.

Every routing change is prompted — by design you are asked before AI-FluxMux changes which model answers.

Use Cloud Usage Mode to select how much usage your cloud model gets.

·        Normal — AI-FluxMux offers a change most readily and most often. A turn that will not fit the loaded Context, one that would overflow into ordinary RAM, or one that clearly asks for cloud, will by default be offered to a ready cloud model if loaded.

·        Low (prefer local) — other ‘better fit’ Local options will typically be offered first if a switch prompt is triggered. Cloud is still offered if your prompt explicitly asks for it.

·        Hold (local only) — stay on Local, whatever the prognosis for the current chat turn looks like.

Under all three, cloud is still used if the local model is down, and all three can still suggest loading a different local profile.

For routing to work most smoothly you typically set one cloud model and one local model running from their respective Quick Select slots at the same time. This works because cloud and local do not compete for the VRAM on your GPU.

AI-FluxMux by design will start your chat using the running local model. Should a capacity situation arise that the hot cloud model running in the background would be significantly better able to handle, you will be prompted to switch to it. You will be prompted to switch back when it looks like the local model can safely take over again.

One thing to know about the offer that follows an overflow into ordinary RAM: it only applies once the loaded local model is already sharing work with your CPU. A model running entirely on the GPU that still fits the turn stays local, however big the turn is.

You can also switch from one local model to another at will, and sometimes you may be prompted to, if Route requests is on and your current chat request looks to exceed the capacity of the current model. That prompt is Load suggested model profile. This is far less smooth, because most of the time a switch means a full local model reload into VRAM, which takes many seconds, and thus a loss of the current chat context used by the earlier model — meaning you probably need to also start a new chat.

Cloud providers

Most major Cloud providers are ready populated on the Servers tab — just pick the provider, paste your key, Validate Cloud Key, Save Key.

Any provider not included needs you to supply a Name and Base URL, then click Add custom provider. You can keep several named custom providers at once, each with its own address and key. Note that a single saved provider key is normally used for all model options the provider offers.

Cline

Once Cline is installed and pointed at your Port, AI-FluxMux keeps its settings in step with whichever model is loaded: the available Context, Images, and which model profile is showing. You do not have to revisit Cline's settings each time you switch models.

  • Install it first. AI-FluxMux does not install or upgrade Cline. Cline is an extension for VS Code, so install it from the Extensions panel there, or use Install guide (Cline) or Cline docs on the Servers tab.
  • Point Cline at your Port once. In Cline's settings choose OpenAI Compatible, set the base URL to the address on the Servers Model API line (no /v1 — Cline adds that), use model id local, and put a single space in the API key. The Cline panel on Servers then says whether Cline is pointing at your Port. Until it is, AI-FluxMux leaves Cline's settings alone.
  • Launch writes those settings. Each Launch writes the loaded Context and the model profile name into Cline's OpenAI Compatible settings, turns off Cline Auto compact so that FluxMux Compact is the one shortening forwarded history (unless the model profile leaves that to the Client app), and leaves Supports Images ticked when a validated Images-on profile exists. Cline shows the profile name as its Model ID, and your Port still takes the turn. If the model bar or those toggles look unchanged, reload that editor window so Cline rereads the files.
  • A new model does not need a new task. Cline keeps model id local, so the next message in the same task uses whichever model is loaded by then. Start a new Cline task when a turn ended in an error that would simply repeat, after you abort a hang, or if Cline is looping the same command.
  • Keep one Cline task per project, the same discipline as one Harness chat per project. Carrying an unrelated job on in the same task fills Context, and compaction then eats the detail you still needed.
  • An older Cline needs its Context set by hand. Cline defaults Context Window to 128000 and does not read Context from your Port. Cline 4.x is written by Launch, as above. On an older Cline, expand MODEL CONFIGURATION (the chevron below Azure Identity) and set Context Window Size yourself.
  • Updating Cline is up to you. Servers has Open Cline releases, and AI-FluxMux never installs or upgrades it. AI-FluxMux keeps running if you close the editor.

DeepSeek Harness

Once you install DeepSeek Harness, AI-FluxMux does the rest: it dynamically writes Harness's settings to match whichever model you have loaded, starts the web UI, and opens the right browser address for you. You do not need to worry about the configuration settings.

·        Install it first. AI-FluxMux does not install or upgrade Harness for you. Use Install guide (DeepSeek) or Harness docs on the Servers tab. You will need Node.js 22.19+ or 24+.

·        Launch a model first, then click Start Harness web on the active Quick Select slot. That one button syncs Harness to the loaded model, starts the web UI, and opens it. Once it is running, the same button becomes Open Harness chat (to create a 2nd chat), and Stop Harness web shuts it down – though any browser tabs created stay open as a record.

·        Do not bookmark the Harness address. Recent versions need a single-use token in the URL, so a saved bookmark shows an error or an empty model list. Use the Start Harness web button instead — it knows the current address, and will restart Harness web if the old page no longer works.

·        In Harness, the AI-FluxMux / local model should be selected. This is usually automatic, but if not, you may need to point Harness Settings → AI-FluxMux model.

·        Start a new Harness chat whenever the loaded model changes. Harness reads any new model settings only when a new chat starts, not on every message, so a new Launch from the newly active AI-FluxMux model profile is needed to pick up the new model limits. AI-FluxMux will open a new Harness browser tab for you when that happens.  Don’t use any stale tabs, as they will be based on out of date settings if they work at all.

·        Keep one Harness chat per project, the same discipline as for Cline tasks.

·        Updating Harness is up to you. Environment → Check for updates compares your version to what is published and offers Open Harness releases — it never installs anything. Back up your Harness settings folder before a preview upgrade.

Switching to a cloud model keeps your current Harness chat. Only a local model reload needs a new one.

If the automatic settings write ever fails, Servers has Copy settings.yaml and Write settings.yaml as a manual retry, and a Harness web UI port field if you need to move it off its default. Ordinary use should not require any of those.

Diagnostics

topic.diagnostics

Live telemetry graph

topic.diagnostics_telemetry_graph

The two graphs at the bottom of Diagnostics have two uses. With Reply speed ticked, each Client-app turn that finishes plots one point: TTFT (s) on top (how long that turn took before the first token appeared) and (tok/s) below (how fast the reply then flowed). The points line up by turn, so you can watch turn by turn whether a model is starting slowly or replying fast. Leave Reply speed unticked and the graphs stay empty, showing No telemetry — that switch is what feeds them, so it adds no work until you turn it on.

The second use is the Stress test below: it drives the same two graphs with a curve of context fill against TTFT and throughput, so you can see where the loaded model starts to slow down or fail. The two uses are separate — a stress test retitles the axes to Context (tok) and clears the turn points, and the next completed turn brings the graphs back to the per-turn view.

Stress test

topic.diagnostics_stress_test

Stress test runs a context-fill probe on the loaded model. It sends requests at rising fill levels — 25% up to 110% of the profile's context limit — and measures TTFT and throughput at each, so you see how the model copes as the context fills. The mode box picks how each level is driven: Progressive (default) builds a realistic multi-turn conversation up to the target and measures the model's real token count each turn, which is the closest to real chat; Single prompt sends one varied prompt per level, which is faster but less faithful.

The test is meant to run to failure. It deliberately pushes past the context limit so you can watch what actually happens — a graceful slowdown, a hang, or a crash — rather than guessing where the wall is. The result appears in the log above and is written to context_fill_perf.log. Use Cancel stress test to stop it early. Run it when the model is otherwise idle: it drives real requests, so it will compete with any chat you are running.

Hail Mary Compactor

topic.diagnostics_hail_mary

Hail Mary Compactor is a last-resort button that appears in the Diagnostics header when the current turn is close to exceeding the loaded context. It deletes the older turns from the middle of this chat's forwarded history so the current turn fits; the most recent turns and your last task are kept, and a short summary of what the removed turns established (goal, decisions, dead ends) is added. Your Client app still holds the full conversation — only what is sent to the model is shortened.

The trade-off is that the model loses the detail of the removed turns, so it may repeat some work. That is still far less disruptive than starting a new chat, where the model loses everything. If a model with more Context is ready, such as a cloud model, switching to it keeps the whole chat instead. Use this button when you want to keep this chat on the current model.

Reply speed monitors the tokens per second being generated by your model reply. In itself this is not a good way to benchmark between Client apps or model performance, but it does show you how hard the model is working. Leave this unticked to save the model server a little work.

The GPU VRAM, GPU util, CPU RAM, and CPU util gauges offer another cheap indication of system activity, but these are also affected by anything else running on your PC.

GPU & VRAM opens a quick overview of current tasks consuming your GPU's memory, which may be competing with your local models. You can use this to hunt down and close unneeded applications, then Refresh VRAM to see how much you have freed up. On a PC with motherboard graphics and a main graphics card, Windows GPU affinity can send other apps to the motherboard GPU. Select Motherboard GPU, click Apply, then restart Windows.

Health generates a summary of the currently active model's health status. In the event of problems, it may offer suggestions. It names the affected thing — llama-server, the GGUF filename, AI-FluxMux, your Client app, or the model profile. The result appears as a banner you can Dismiss.

Copy log copies the current contents of the system log to the clipboard, for sharing with a person or AI who is helping you diagnose and troubleshoot any problems.

Clear clears the current log. Sometimes useful as a way to exclude what is not relevant when reproducing an issue you want diagnosed.

Idle timeout stops an unused local model after the minutes you set, which frees VRAM for other applications. A reply that is still being written never counts as idle, however long it takes, and working in the AI-FluxMux window keeps it awake too. Your next chat message reloads the model, which takes time and starts that model's context clean. Leave it off to keep the local model loaded and ready.

UI scale (Normal, Compact, Very Compact) and UI theme (light or dark) sit in the same strip.

Routing decisions

Routing decisions appear here as banners, with the same buttons as the pop-up prompt. The ones you will see most:

·        Continue waiting — llama-server is slow to start a reply, but is still working. This keeps your current chat turn open, and the same choices come back after another wait. Thinking models can sit without tokens for a while, even on a short hello, so this is usually the safe first click.

·        Switch to the named model — sends this turn to the hot cloud model, or back to the loaded local. If that switch needs a fresh Harness chat, the button says so.

·        Keep current model — this turn continues — you were offered a switch, but this turn is still running and stays where it is.

·        Keep current model — end this turn — stay on this model, but the current turn is finished. Start a new chat rather than adding to that one.

·        Load suggested model profile, Compact, or Keep current model profile — offered when Context is filling, or when another validated profile would suit this turn better. Loading a different local model reloads llama-server, so start a new chat after it.

·        Or choose a different model — opens a list of your other launched or validated models; pick one and click Switch to selected.

Ports

Three different ports are used by AI-FluxMux.

Name

Who uses it

5001

Port

Any Client apps (Cline, Harness, or any OpenAI Compatible client) use this to talk to AI-FluxMux. The Client app and AI-FluxMux must be set to use this same port. Several Client apps can use it at once.

·        Make sure no other applications you run use any of the ports AI-FluxMux uses.

·        In the event of a clash, change port settings in those other apps, or in AI-FluxMux and the Client apps AI-FluxMux talks to, as needed.

·        Do not point a Client app at llama-server.exe, and do not adopt an already-running listen port as your Port if you want AI-FluxMux to switch models for you.

·        This version of AI-FluxMux is only tested for use where the Client apps, llama-server, AI-FluxMux, and GPU are all on the same PC. If you want to reach AI-FluxMux from other networked machines, or remotely, you could probably use a tunnel (SSH or Tailscale) on the GPU box.

·        Do not router-forward these ports, and do not paste a remote listen address into them.

Port rules

topic.port_rules

Port rules watch how a local Client-app turn is forwarded to llama-server. Cloud models do not use Port rules. When a rule is off, FluxMux does not apply that check. Compact, Omit, and Max pictures only change the pack forwarded to llama-server. The Client app still has the full chat.

Mill at omitted is how deep that forwarded pack is (older tool bodies stubbed) before FluxMux inspects the latest tools. If those latest tools still look like useful project work, that rule does not pause. Useful project work means the latest tools still touch the job: edit, read, search, test, build, or run, including looking at the project afterward.

A pause holds this Client-app turn and asks: Send this turn anyway, End this turn, or Let me steer. A ready cloud may also be offered.

Rule What it watches When it treats the turn as a problem What FluxMux does
Compact Forwarded chat versus Context Older turns are filling Context Shortens the pack forwarded to llama-server. Does not end the turn. The Client app still has the full chat.
Omit Full tool results on the pack Older tool bodies are large Stubs older bodies so llama-server still sees that the call ran. A result identical to an earlier one still shown in full, such as a file read again unchanged, becomes a one-line pointer to it. Does not end the turn. The Client app still has the full output.
Max pictures Pictures on the pack More pictures than this setting Drops the oldest pictures from the pack. Does not end the turn. The Client app still has the album.
Mill at omitted Count of stubbed older tool bodies That count is high and the latest tools are not useful project work Pauses this Client-app turn.
Closed-loop lookback Latest tools This is the window size only How many recent tools are read when judging useful project work. Does not pause on its own.
Closed-loop mill ceiling Stubbed older tool bodies That count is huge even if the latest tools still look useful Last-resort pause.
Observe-only mill Latest tools Only screenshots or browser views, with no read, edit, search, or run-test Pauses even on a short chat.
Repeated command Latest shell commands The same command again Tells the model first that the result will not change. Pauses this Client-app turn only if it runs the command a third time.
Failed calls Latest tool results Three or more failed in a row, even with different commands Tells the model to read the errors and change approach. Does not pause.
Diagnostic dump Session-created files Too many dump files instead of editing project files Pauses this Client-app turn.
Hang Quiet llama-server No first token, or silence mid-reply Pauses mid-stream.
503 llama-server still loading Loading / 503 Retries. Ends the turn only if the retries run out.
Client-app max tokens This turn's max tokens A choice, not a pause Profile overlay, the Client app, or the smaller of the two. Reply is still clamped so prompt plus reply fit Context.
Stop strings Client-app stop list A choice, not a pause Pass the list through, or ignore a list that can short-loop or cut thinking.

Local detailed settings

The chart below lists the settings AI-FluxMux uses for a local model profile. Most have a control under Detailed settings on the Model Profiles tab, but some seldom-used advanced settings are deliberately not exposed, though they can be adjusted by direct edits to the model profiles configuration file (see Appendix A).

AutoTune and the User priorities wizard can change many settings automatically, but both leave your hand-tuned temperature, reasoning, chat format, Compact, and multi-GPU choices alone, and never lower a Context or max tokens you set. Images is a user setting that both will always work around rather than adjust.

Legend: no mark = control is in Detailed settings. † = control is in Detailed settings but hidden until a specific condition arises (see Notes). ‡ = no panel control — the value lives in saved profile JSON, or is chosen by AutoTune / AI-FluxMux at launch (listed in Appendix A).

Fit and memory

Setting

What it does

Notes

Context

How much chat history llama-server can keep in mind for one session.

Larger uses more graphics memory (VRAM). Changing it usually needs a reload. AutoTune sizes this from leftover GPU memory after Images. AutoTune will not lower a hand-tuned value, except the editor max (262144), which is not a measured fit.

Flash

Flash attention for long chats.

Enabled or Disabled. Usually makes long chats faster and lighter on graphics memory. Leave Enabled unless a model misbehaves with it.

Fit VRAM

Lets llama-server shrink launch settings to fit available VRAM.

Ticked = safer launches when memory is tight. Unticked = keep the sizes you set.

KV key

Storage precision for attention Keys — how reliably the model connects new text to the right earlier turns.

Prefer q8_0 or f16, the most faithful. q5 or q4 fit roughly twice the Context in the same graphics memory, but recall of earlier turns is weaker: worth it when Context matters more than Fidelity. The priorities wizard and AutoTune stay at q8_0 or higher unless you rank Context length above Fidelity. Set KV key and KV value the same unless you are tuning on purpose.

KV value

Storage precision for attention Values — how faithfully the content of earlier turns is kept.

Same trade-off as KV key. Usually match KV key.

SWA full

Sliding-window attention full cache on supported models.

Try Enabled if long chats forget recent turns.

Cache reuse

Reuse work from similar earlier prompts.

Can make follow-up questions start sooner.

Cache RAM

How much ordinary RAM to keep for that reuse.

Unlimited helps long back-and-forth chats. Disabled turns reuse off.

Trim waste per turn (forward pruning)

On every turn, tidies up the conversation before sending it to the model — removes duplicate messages and collapses repeated tool calls. Rarely has a big effect, but keeps the prompt lean.

On by default. Toggle takes effect on the next turn, no reload needed. Greyed out when long chats are shortened by the Client app (see Long chats are shortened by).

Page context (lossless spill)

When a tool result is too large to keep in full, the complete output is saved to a file and a short reference is kept in the prompt instead. The full output is available in the context_swap.json file if you need to read it back. When off, the output is cut down to a short preview (the old behaviour).

On by default. Only matters when a tool result is genuinely large. Toggle takes effect on the next turn, no reload needed. Greyed out when long chats are shortened by the Client app (see Long chats are shortened by).

Long chats are shortened by

Who shortens a chat that grows too long for this profile's Context. AI-FluxMux, Port rules settings: AI-FluxMux summarises older turns using Compact in Port rules. AI-FluxMux, this profile's settings: the same, using this profile's Trigger, Keep turns, Tool results and Pin user. The Client app: AI-FluxMux sends the chat on as the Client app sent it, and the Client app shortens it itself (Cline Auto compact, or Harness's own shortening).

With either AI-FluxMux choice, your Client app still keeps the full chat, and Launch turns Cline Auto compact off. With The Client app, Launch turns Cline Auto compact back on (if AI-FluxMux turned it off), pruning and paging are not used, and AI-FluxMux still shortens the chat as a last resort when it reaches 95% of the Context, so the turn runs instead of failing. Applies from the next message.

Keep session vibe (VIBE_STATE.md)

Keeps a short note of this chat's task, progress and next step, and passes it to the model each turn, so it keeps its place after the chat is trimmed or the model restarts. Each chat keeps its own note, updated automatically after each turn. Hail Mary uses it to rescue a chat that ran out of room. You can read and edit the current chat's note in VIBE_STATE.md.

On by default. Applies from the next message, no reload needed. It does not slow replies: the note rides on your newest message, so the rest of the prompt can still be reused.

Git checkpoint folder

The folder where the "Checkpoint" button (and the model's git_checkpoint tool) creates git commits. Leave blank to use the workspace root (the parent of the config file's folder). Pick a different folder if your git repo lives elsewhere. The folder must be a git repository for checkpoints to work.

Defaults to the workspace root. Use Browse to pick a folder, or Reset to go back to the default. Takes effect immediately on the next checkpoint, no reload needed.

User priorities wizard

Rank the goals with the up and down arrows, or drag them. The top of the list matters most when AI-FluxMux fills in settings. Local profiles offer Stability, Speed, Fidelity, Context length, Reply length, and Reasoning depth. Cloud profiles swap Fidelity for Token Cost Economy. Local goal tips talk about VRAM; cloud goal tips talk about token cost.

On a local profile the list also follows your hand edits: when a setting you change clearly favours a different order, the list moves to match, and the line under it says what the change trades. Use the arrows to put it back if you disagree.

AutoTune applies that ranking to the settings on the form. Save profile keeps what it wrote; Revert changes discards it. On a local profile you can also tick Test local system for additional optimisations (experimental) first. AutoTune then reloads the model a few times and times real replies, trying Micro-batch sizes and, on MTP models, draft lengths, and keeps only clearly faster settings. It takes a few minutes, and progress shows in Diagnostics. Cloud AutoTune has no such option.

AutoTune, graphics-memory, and speed numbers are estimates, not promises. While you can spend many happy hours tweaking and benchmarking your models and profile variants, you should test important setups by launching the model and seeing how it actually runs under the tasks and conditions you need to throw at it.

Warning icon (⚠)

⚠ means this profile is not trusted right now. That can be: the last Launch or Validate to endpoint failed, you saved a launch-critical change since the last successful Validate to endpoint (so the last good connection may no longer hold), or a local model file is missing from the folder you set on the Servers tab. Quick Select Launch and Restart stay off until Validate to endpoint succeeds again, and the icon clears only then. That successful validate also refreshes the Quick Select summary from the live Model Profiles entry.

Saving only a temperature or max tokens change does not raise the triangle, because neither needs a fresh launch to be trusted.

Model switch performance testing

On Live-Switch Testing, nominate any two validated cloud or local profiles as Profile A and Profile B. The test launches A with a set task, hands the chat to B, returns to A, and scores how much of that task survived the trip. It unloads and reloads, so it is a controlled test rather than everyday routing.

Stopping and recovering

Stop ends the model managed by that Quick Select slot. Stopping a local route closes llama-server and frees graphics memory after the process exits. If launch fails, Stop remains safe to use while AI-FluxMux cancels startup. Check Diagnostics for the reason, correct the setting on Model Profiles, Validate to endpoint again, then Launch from Quick Select. If cloud was paused for quota or rate limits, fix billing or wait, then Launch the cloud slot again — that clears the pause for that profile.

AI-FluxMux window does not open

You should get a Windows error titled AI-FluxMux could not start. The same steps are written to AI-FluxMux-could-not-start.txt next to FluxMux.Avalonia.exe. You can open this Help.html file in a browser while the app is down.

If the window flashes and disappears, unzip a fresh copy of the release over that folder and start FluxMux.Avalonia.exe again. Your settings are in %AppData%\AI-FluxMux\ and are not touched by that.

If the window is missing after you unplug a monitor, start AI-FluxMux again — it ignores a saved position that is no longer on a screen. Starting it also ends any previous copy, including one with no window. Closing the window ends that process too, after llama-server has been asked to stop.

If Health says the settings file could not be read, AI-FluxMux renamed the broken file with a .bak- date suffix beside it and started with empty settings. Your previous file is not deleted.

Environment and troubleshooting

The Environment tab checks llama-server, configured folders, the selected company's keys, and local models in the folder. Check for updates can replace Help.html from a feed URL when one exists, can offer a matching llama-server zip for the folder already in use, and can show your DeepSeek Harness version against what is published. Confirm that llama-server install still matches this GPU before you update — hardware may have changed. AI-FluxMux never extracts over the current llama-server folder, and does not install or upgrade DeepSeek Harness.

Picture support is guessed from filenames until launch. Unban tokens is a real llama-server option (--unbantokens) when llama-server's help lists it; AI-FluxMux only sends it then.

Performance settings

Larger Context and higher GPU offload need more VRAM. Optimistic profiles that push Context, max tokens, Images, and GPU offload all the way up are common; they are not a request to fill the window. Fit VRAM can still shrink a launch so llama-server starts. A ready cloud profile is how Route requests can take a large turn without waiting for that maxed Context to fill. KV key and KV value set how precisely llama-server stores attention Keys (linking back to earlier turns) and Values (keeping earlier content). Prefer q8_0 or f16. Below q8_0 fits more Context but recalls earlier turns less reliably, so the priorities wizard only chooses lower when you rank Context length above Fidelity. Flash attention can reduce memory use or improve throughput when the runtime and hardware support it. Start conservatively, check readiness, and compare measured results for your model and hardware. See Local detailed settings for a control-by-control summary.

GPU & compatibility

This version has been developed and tested on an NVIDIA GeForce RTX 5090 on a Windows 11 PC.

It has been written to detect and work with whatever hardware is found, and should work fine with other NVIDIA RTX GPUs, and even with other AI-capable GPU families (AMD, Intel) to varying extents — but other combinations are not qualified until the relevant hardware is available for testing (donations gratefully received).

Appendix A — Model profile settings (JSON)

Use this when a setting has no Detailed settings control (marked ‡ in the local chart), or when you need an exact value the panel does not offer. All profile settings live in a single config file.

Which file, and where

·        Profile settings: fluxmux_config.json, usually in %AppData%\AI-FluxMux\.

·        Confirm your path first: on startup, the status line at the bottom of the window shows Loaded configuration from … with the full path. Use that file — a build from source keeps its own copy elsewhere.

·        Cloud API keys live in fluxmux_secrets.json, not in profile objects. Do not copy out secrets, or share the config file.

Safe edit steps

1.       Back up fluxmux_config.json first.

2.       Close AI-FluxMux before editing, or edit only keys you are not changing in the open session — Save profile in the app overwrites panel fields and may clear Validate until you test again.

3.       Find the correct profile key under LocalProfiles or CloudProfiles.

4.       Add or change a property inside that object. Keep valid JSON (quotes, commas). Key spelling is exact — see the ‡ table above for launch-only local keys.

5.       Save the file, relaunch AI-FluxMux, open that profile on Model Profiles, and run Validate to endpoint (or Launch from Quick Select) so launch-critical changes are tested.

Example (local, launch-only key)

Inside LocalProfiles, under an existing variant object, you might add:

"LocalReasoningEffort": "medium"

Full shape (your file will already have many other keys on the same object):

{
  "LocalProfiles": {
    "Qwen3.8-27B-Q4_K_M.gguf::Long context": {
      "OverrideContext": "131072",
      "LocalReasoning": "On",
      "LocalReasoningEffort": "medium",
      "LocalTemperature": "0.3",
      "PriorityOrder": ["Context length", "Fidelity", "Stability"]
    }
  }
}

Replace the key and filename with yours from Model Profiles. Extra keys you add are kept until you remove them; the panel does not delete unknown JSON properties when you Save profile.

Appendix B — Model profile packs

These are temporary transfer packs, not a second live store. The running copy of your profiles stays in fluxmux_config.json. Use Export and Import when you want a recovery copy after a bad edit or a reinstall, without copying API keys.

·        Export model profiles on Model Profiles writes your local and cloud profiles to a pack. No API keys. Validate stamps are stripped, so a new PC must Validate to endpoint again. Keep the pack somewhere that survives an uninstall.

·        Import model profiles adds profiles that are not already there. Before it changes anything it writes a pre-import pack of your current profiles beside the config file, and if it does add rows it also leaves a timestamped fluxmux_config.json.bak-profiles-… copy. Restore that .bak copy if you need the exact previous file back.

·        Import rejects a file that contains secrets, script markup, a full live config, or an Endpoint adapters pack.

·        Import never overwrites one of your existing rows. A profile with the same name but different settings is skipped, and so is one whose .gguf is not in your model folder, or which has Images on with no matching mmproj projector. Every skipped row is listed on Diagnostics, so check there afterwards.

·        Put the matching .gguf and projector files in your model folder, then Import again to pick up anything that was skipped. Validate to endpoint each imported row before you Launch it.

Appendix C — Endpoint adapters (JSON)

Cline and Harness are handled for you. Use this appendix only if you want a third OpenAI Compatible client kept in step with the loaded model as well, or if a hand-edit went wrong.

The config key, the example file, and the two Servers buttons all still say Endpoint rather than Client. That is the original name and it is kept so existing settings files and exported packs keep working. It means the same thing as Client app everywhere below.

·        Live settings: the EndpointAdapters array in fluxmux_config.json. If that key is missing, the built-ins stay on: cline-4x and harness-yaml. Listing an id with enabled false turns that writer off.

·        When writers run: every time AI-FluxMux changes which model answers on Port — after a Launch completes, after an approved routing switch, when you change the Client app, and after an adapters import. It is not only on Launch.

·        Portable pack: Servers → Export Endpoint adapters. That writes Port, Client app, Harness web port, and EndpointAdapters only — no API keys and no model profiles. Keep it somewhere that survives an uninstall.

·        To recover a bad edit: Import Endpoint adapters and pick that pack, or endpoint-adapters.example.json next to the app. Import backs up your live config first.

·        To add a client: copy an object from endpoint-adapters.example.json into EndpointAdapters. Kind json-merge writes tokens such as {context}, {advertisedContext}, {maxTokens}, {displayName}, {imagesOn}, {reasoningOn}, {port}, and {modelId} into that client's own JSON settings file, at the dotted paths you list under set. It never creates the file (onlyIfFileExists defaults to true), and baseUrlPath skips the write unless that client is really pointed at your Port.

{
  "id": "example-openai-client",
  "kind": "json-merge",
  "enabled": false,
  "path": "%USERPROFILE%\\.example-client\\settings.json",
  "onlyIfFileExists": true,
  "baseUrlPath": "provider.baseUrl",
  "set": {
    "provider.model": "{modelId}",
    "models.local.name": "{displayName}",
    "models.local.contextWindow": "{context}",
    "models.local.maxTokens": "{maxTokens}",
    "models.local.supportsImages": "{imagesOn}"
  }
}

Close AI-FluxMux before hand-editing the config, keep the JSON valid, and do not replace the whole config file with the example. Then Launch so the writers run again, and reload the client so it rereads its own files.

Why Cline and Harness need this

Both were built for a remote API, where a model id names one model of fixed capacity that never changes underneath it. A local router breaks that assumption: the id stays local while the model behind it, and its Context and reply length, change whenever you Launch.

Nothing in the OpenAI API covers that case. A model list carries an id and little else, and the fields that describe capacity, such as context_length and max_model_len, are conventions individual vendors invented rather than part of any specification. AI-FluxMux publishes them at Port, along with the reply length and whether Images are on, so a client that reads them keeps up by itself. Neither of these two does.

·        Cline treats an OpenAI Compatible provider as something you configured, so Context Window is a number you typed, and it defaults to 128000. Cline fetches the model list to fill its picker, but takes capacity from its own settings. Its Auto compact then decides when to summarise against that typed number rather than against the model actually loaded, which is why Launch turns Auto compact off and leaves shortening to FluxMux Compact. When the model profile's Long chats are shortened by is set to The Client app, AI-FluxMux leaves the shortening to Cline, so Launch leaves Cline Auto compact on, and turns it back on if AI-FluxMux was the one that turned it off.

·        DeepSeek Harness reads settings.yaml when a session starts, not on each message. A session already under way keeps the capacity it began with, which is why a new chat is needed after those settings are written.

A wrong number is not fatal. An oversized turn is compacted, clamped, or turned into a routing offer rather than being handed to a model that cannot take it. Keeping the client in step simply means fewer of those interruptions.

Clients that may need no adapter

AI-FluxMux reports the loaded model at Port using the same field names llama-server uses, so a Client app written to read a llama.cpp server can follow a model switch by itself. Each entry in the model list carries the loaded Context as context_length, max_model_len, and meta.n_ctx; the reply budget as max_tokens, max_output_tokens, and meta.n_predict; and whether Images are on. The list is built when it is asked for, so the answer changes as soon as a different model takes the turn.

Two things are worth knowing before relying on that. There is no standard for any of it, so a client reads these fields only if its author chose to, and many ask only when a session starts or when a model is picked rather than on every message. AI-FluxMux also states a capability only when it knows one: before anything is launched the reply budget is left out rather than guessed, because a client told a wrong number is worse off than a client told nothing.

To find out where your own Client app stands, load one model profile and note the context it reports, then Launch a profile with a different Context and look again. A client that reads Port follows the change with nothing written to its settings. One that does not will keep showing the old number, and that is the case an Endpoint adapter exists for.

Appendix D — Developer notes

For anyone who wants to build AI-FluxMux from source or extend it. Not needed to use the app.

Building

·        .NET 10 and Avalonia. One application project plus one test project.

·        dotnet build and dotnet test in the application folder, with AI-FluxMux closed. That produces the debug launcher.

·        If AI-FluxMux is already running and holding a file lock, build to a side folder instead — dotnet build -p:UseAppHost=false -o artifacts\test-ref. Never launch from that side folder, and never let it overwrite the debug output.

·        Startup failures are written to FluxMux_Startup_Error.log.

Where the logic lives

The source layout is mapped in AGENTS.md in the repository, area by area. It is kept there rather than here so there is only one copy to keep current as files move.

Extension points

·        A new cloud provider. Add it to the registry in CustomCloudProviderRegistry.cs if it should ship as a ready-made entry. Anything OpenAI Compatible needs no code at all — the operator can add it as a custom provider with a name and base URL.

·        A new Client app. Prefer a json-merge adapter in config (see Appendix C) over new code. Write a real adapter class only when the client needs a non-JSON file, as Harness does with yaml.

·        This Help file is the copy store. Heading 2 becomes a Help index topic. The Interface notes heading is excluded from the index, and each Heading 3 under it is an id for a note shown next to a control in the app, resolved at runtime by HelpUiNotes. Saving the file refreshes both the Help tab and those notes without a rebuild.

·        Behaviour worth reading before changing: only one llama-server is ever loaded; Compact must not run on every turn; prompt-size estimates must not count embedded image bytes as text; routing changes are offers, never automatic.

Do not change

·        C# namespaces.

·        JSON key names in fluxmux_config.json, and the shape of fluxmux_secrets.json — both are live operator data.

·        The FluxMux protocol string used to recognise export packs.

·        Local model discovery: *.gguf, with mmproj in the name meaning a vision projector rather than a model.

Appendix E — Harness settings.yaml

Launch writes the provider block DeepSeek Harness needs, so ordinary use never needs this appendix. The two buttons on the Servers tab are a manual retry for the rare case where that write fails.

·        Copy settings.yaml builds the provider block for the model profile most recently loaded in Quick Select and puts it on the clipboard. It is not a copy of the file on disk, so it shows the current profile rather than whatever Harness was last given.

·        Write settings.yaml builds the same block and merges it into %USERPROFILE%\.dsh\settings.yaml — the same path and the same merge the automatic write uses. The previous file is kept as settings.yaml.bak.

If Write keeps failing, which usually means a permissions problem or Harness holding the file open, use Copy and paste the block into that file yourself. Start a new Harness session afterwards either way, because Harness reads these settings when a session begins and not on every message.

Prompt for any AI editing this file. You are changing operator-facing copy only. Do not treat this as a request to rewrite C#, XAML, Health, 400s, or routing dialogs.

This is the one copy file. Help topics are Heading 2 (except this heading). Standing notes on Quick Select / Servers are Heading 3 ids under this heading. A setting Help link keeps a Heading 3 under its topic whose only text is an id that starts with topic. (for example topic.port_rules). That heading is not shown. Save as Microsoft Word Web Page, Filtered, keep the name Help.html, in this folder or next to AI-FluxMux.exe. Turn off Word smart quotes and the dash that turns -- into a long dash. Put yaml samples in Preformatted text or a one-cell Consolas table. Newest Help.html next to the exe or in the start folder wins.

House style is the Microsoft Writing Style Guide, with the house overrides set out below. Write in second person and present tense — you click, AI-FluxMux writes, llama-server reloads — and in the active voice. Headings are sentence case. Say what to do before why it matters, and keep each sentence short enough to read while standing in front of the window. Spell out one to nine and use numerals from 10 up, except for a version, a port, or a setting value. No exclamation marks and no "please". Cut "simply", "just", "note that", "in order to", "allows you to", and "we recommend" — give the instruction instead. Write "for example", not "e.g.".

Prefer the plain word over the insider one wherever the plain word says as much. Switch to the cloud model rather than hop to it; AI-FluxMux writes the settings for you rather than handling the plumbing; a model is busy rather than exhibiting busyness. The reader is an operator standing in front of the window, not someone who has read the source. Keep the domain terms they genuinely need — Context, VRAM, token, quantisation, projector — and keep every term in the vocabulary list below exactly as it is spelled there. Everything around those terms should read as ordinary English.

Five house rules override that guide where they disagree. Spelling is British and New Zealand English: behaviour, licence, optimise, recognise, synchronise — do not Americanise them. Contractions are avoided, so write "do not", "cannot", "is not"; most of these sentences are warnings, and the full form carries more weight. A button is clicked, not selected. Product terms keep their capital in mid-sentence — Port, Context, Compact, Images, Reasoning, Max tokens, Client app — because each one names a control or a term from the vocabulary list below. And a heading that names a control is spelled exactly as the window spells it: User priorities wizard, not User Priorities Wizard.

Three character styles carry meaning, so keep them apart. Bold is a control the operator clicks, ticks, or reads as status — a button, tick box, field label, group heading, dropdown value, or state line — whether it belongs to AI-FluxMux or to another named app such as VS Code, Word, or Windows. Italic is emphasis, the run-in label that opens a bullet, and a cross-reference to another topic or appendix in this file. Consolas is a path, file name, extension, JSON key, command, address, or a literal value the operator types. Never use bold for emphasis: that is what stops a control name standing out.

Four things stay unbolded on purpose. Tab names (Servers, Model Profiles, Quick Select, Diagnostics, Environment, Help) read as plain proper nouns, so bold is left for what is clicked inside them. A feature discussed by name rather than clicked — AutoTune sizing a Context, Compact shortening history, Health explaining itself — is plain; bold it only where the operator presses it. In the settings tables the first column is already the control, so it is not bolded again, and plain-English states such as Enabled, Auto, or Ticked stay plain there too. Do not invent control names: copy the label off the window.

Under a Heading 3 note id the app renders bold only, so italic and Consolas fall back to plain text in those paragraphs. That is why the short run-in labels in the routing note are bold rather than italic.

Every Heading 3 id below matches one note in the window, so do not rename or invent them, and edit only the paragraphs under an id that is already there. Deleting an id is how a note is removed from the window, so delete one only when the note is meant to go. Do not add Health, Diagnostics, Client-app 400s, or confirm-dialog copy here. Do not type a Port number, a Harness version, a key, or a path here, because those change: write {Address} for the address a Client app calls, {Port} for the port alone, or {ProfileContext} for the Context of the model profile on screen, and AI-FluxMux fills them in as it draws the note. A name it does not know is left showing as you typed it. A note keeps the shape you give it, so several short bullets read far better on screen than one long paragraph.

Say AI-FluxMux, Port, daemon port, llama-server, local model, model profile, Client app, Compact. Do not say the runner, the backend, or Endpoint app — the calling program is the Client app, and the endpoint is the address it calls. The EndpointAdapters key, endpoint-adapters.example.json, the Export Endpoint adapters and Import Endpoint adapters buttons, and the Endpoint settings group header keep that older word on purpose; leave them alone. Route requests always asks first; it never changes model on its own. A local-to-local llama-server reload is not safe in the same Harness chat.

Heading 1 is the title or a banner. A banner is not itself a Help index entry, but it groups the entries under it: every topic that follows one is listed beneath that banner in the index, until the next banner. Keep a banner short enough to read as a group label. Heading 2 is a Help index topic, except this Interface notes heading, which must stay spelled exactly that way. Heading 3 inside a real Help topic is a subheading, not a note id. Do not add another Heading 2 named Interface notes. The Help tab sizes the three levels differently, so use them for what they are rather than for how large the text looks.

Two Word features carry through to the Help tab. The Quote paragraph style becomes a tinted box, for the short warning an operator must not skim past — keep those to a sentence or two, and leave the ordinary explanation as body text. Insert → Pictures becomes a screenshot; type a caption into the picture's Alt Text, because that is what appears beneath it. Word writes pictures into a companion folder beside Help.html, so that folder travels with the file: without it the picture is skipped and the surrounding copy still has to make sense on its own. Crop a screenshot to the panel being described rather than the whole window.

A third Word feature carries through: a link from one topic to another. Press Ctrl+K, and in Address type # followed by the exact Heading 2 text of the topic being pointed at, as in #DeepSeek Harness. The Help tab matches that on the heading itself, so nothing has to be kept in step by hand, and it ignores the spaces and punctuation if Word rewrites the address. Word may report the bookmark as missing when the link is clicked inside Word; bookmark the heading with that name to silence that, or ignore it, because the Help tab resolves the link either way. An address that names no topic is handed to the browser, so an outside link still works as it always did.

quickselect.intro

Quick Select only runs profiles that already passed Validate to endpoint on the Model Profiles tab. Choose a validated profile in a slot, click Save, then Launch. A newly validated copy is offered on the first empty row. You cannot add another slot while a populated slot is still unsaved.

quickselect.route_requests

Off: only one model answers at a time. On: a ready local and a ready cloud can both take turns on Port; AI-FluxMux asks before a switch, and Cloud Usage Mode sets how often cloud is offered.

quickselect.popup_routing

When Route requests needs a decision (Keep current model — end this turn, Keep current model — this turn continues, or Switch to the other ready model; Load suggested model profile; Compact; Keep current model profile), open a small always-on-top window so it is not hidden behind Harness or another Client app. The same buttons also display in the Diagnostics panel.

quickselect.hot_routing

Dynamic Model Routing. Instant Switching: move between an active local and a ready cloud in the same chat without losing context. Local-to-Local Delay: switching between different local models reloads llama-server into VRAM — slower, and that chat's in-memory context is cleared. Smart Economy: starts local, then offers the ready cloud if this turn would overflow into RAM or cloud is requested. Override that anytime in Cloud Usage Mode.

quickselect.cloud_usage

Cloud Usage Mode sets how often (or if) routing can direct a selected cloud model to take a chat turn (fast). Prompted local routing (slower) will still apply when cloud is not used.

servers.cline_hint

·        Cline API Configuration settings: OpenAI Compatible, base URL {Address} (no /v1 — Cline adds that), model id ‘local’, API key one space character.

·        Launch of any model thereafter auto writes that current model Context and profile name into Cline settings.

·        Launch also turns off the Cline Auto compact function, because FluxMux Compact is what shortens forwarded history. When the model profile leaves shortening long chats to The Client app, it leaves Cline Auto compact on instead. It also leaves Supports Images ticked when a validated Images-on profile exists.

·        Reload the editor window if the new model profile name does not appear in the bar below the Cline task dialog, or the Context window size display looks unchanged. AI-FluxMux will keep running.

·        After new model Launch The next message in the same Cline task uses the newly loaded model. Start a new task if the same error repeats in current task after switching models.

servers.generic_hint

·        Point your Client app at Port. The address is the Model API line beside the Client app box, and the model id is local unless your app needs another one.

·        If your app reads model details from Port it needs no setting up: AI-FluxMux publishes the loaded model's Context, reply length, and whether Images are on, and updates them when the model changes.

·        If it does not, set that app's own Context and reply length to suit the model you load, and revisit them whenever you change models.

·        To have them written for you, add an Endpoint adapter: a small block of JSON naming the app's settings file and which keys to set. It runs after a Launch, after an approved route switch, and on import, and only writes a file that already points at Port, so no app is redirected behind your back.

·        Click Export Endpoint adapters, add your entry to the saved file, then Import Endpoint adapters. See Appendix C — Endpoint adapters (JSON) for the keys and a worked example.

·        DeepSeek Harness is a built-in adapter of the same sort, writing yaml rather than JSON; see Appendix E — Harness settings.yaml.

gpuvram.desktop_gpu

Local AI models benefit from as much VRAM as possible.

  • To stop Windows allocating your main GPU card's VRAM to other apps and system processes, you can try the experimental tool below, to make them use your motherboard GPU & shared ordinary system RAM instead, next time they are launched.
  • In the Windows GPU affinity setting below, select Motherboard GPU, click Apply, then restart Windows (for best results - you can instead just restart individual apps, but this is usually less thorough).
  • A BIOS setting change is usually required before the motherboard graphics chip can run alongside the main graphics card. Do this first.
  • Monitors should be plugged into the motherboard graphics ports, not the main GPU ports. Typically they can be left there even when you switch back – in normal Discrete GPU mode, Windows can still usually route everything to the main GPU card via those ports (with a very small performance hit).
  • If you can't or don't wish to use your on-board motherboard graphics, you can still try closing any unused browser windows and idle apps you started, then click Refresh VRAM below to see how much memory comes free. Only close web pages and apps you opened yourself. Ending Windows background processes could freeze or crash your PC.
  • Note that AI-FluxMux will show up as a VRAM using process (for obvious reasons) whichever GPU affinity mode is set. Don't close this!
  • Your motherboard graphics chip and its ports will likely not match the performance or features of your discrete graphics card for 3D speed, refresh rate, HDR, or how many displays you can connect. Apply Discrete GPU mode and restart again, when you need that extra functionality back.
