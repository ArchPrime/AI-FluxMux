## YaRN "Extend context into RAM" (this session — compiled + tested, NOT deployed)

A per-profile opt-in that lets AutoTune/wizard exceed the model's native context window by stretching it (YaRN) and letting the overflow live in ordinary memory, plus a manual "compact back onto the graphics card" prompt.

- **New per-profile settings:**
  - `LocalExtendContextIntoRam` (bool, default false) — the "Extend context into RAM (YaRN)" checkbox.
  - `LocalYarnMaxContext` (Auto / 512K / 768K / 1M, default Auto) — how far YaRN may stretch the context. **Auto** assesses installed RAM and picks a safe target; the fixed options are explicit targets (user manages other apps).
  - Both wired through `MainViewModel.cs` (property, options, change handler, save/load, all 3 capture methods, `BuildLocalVariantSettingsObject`), both fingerprints, and `MainWindow.axaml` (checkbox + "Max YaRN context" ComboBox).
- **RAM-bounded extension** — `LocalPrioritySettingsCalculator.Calculate` gained `extendContextIntoRam` + `yarnMaxContext`. When on AND context is a top priority:
  - Target = min(user's YarnMaxContext target, RAM-bounded ceiling, 1M YaRN practical limit).
  - `RamBoundedYarnCeiling` computes how many tokens of KV fit in (total RAM − conservative reserve of max(16GB, 25%)), added to the VRAM-resident window.
  - `LocalRopeScaling=yarn` + smallest standard scale reaching the target (options now include 8×).
  - `LocalGpuOffloadMode` forced to `GPU + CPU`; `LocalCacheRam` raised to `Unlimited`; **`LocalFit` disabled** (overflow is meant to live in RAM).
  - The context NumericUpDown maximum rises to ~1M when YaRN is enabled (`LocalVariantContextMax`).
  - `ModelMaxCtx` now uses the model's **true native trained window** (from the GGUF `context_length`), not the editor-capped value — so extension can actually trigger.
- **Manual spill-compact prompt (reuses the existing routing/consent dialog)** — when a YaRN-extended session's live prompt exceeds the VRAM-resident context, `FluxMuxGatewayHost.OfferSpillCompactIfNeeded` surfaces the existing local-reload banner in "compact in place" mode (no auto-compaction). The runtime service stamps `local_extend_context_into_ram` + `local_vram_context` into state at launch; the host reads them. Clicking **Compact** → `AnswerLocalReloadRecommend(enableCompact: true)` → next turn auto-compacts the forwarded history back under the VRAM line.
- **YaRN context stats in model displays:**
  - Profile editor footprint text: `native window N (YaRN extends to M, ≈X GiB overflow in RAM)`.
  - Quick Select slot display: `ctx M (YaRN)` second line.
  - Loaded-model summary row: `ctx M (YaRN)`.
  - Variant-creation status message: "YaRN extends the native N window to M."
- **Effective KV bytes per token (hybrid-KV + Flash Attention aware):** the RAM-bounded YaRN ceiling and the footprint overflow estimate now use the *effective* KV bytes/token rather than the raw profile KV type. `LocalHardwareLaunchAdvice` gained `HybridKv` (populated from the GGUF shape / Qwen3.8 detection). `MainViewModel.ComputeEffectiveKvBytesPerToken()` resolves the profile KV type via `ResolveKvBytesPerToken`, then applies a 0.38 factor for hybrid-KV models and a 0.75 factor when Flash Attention is enabled. This value is passed into `LocalPrioritySettingsCalculator.Calculate` (new optional `effectiveKvBytesPerToken` param) and used by `RamBoundedYarnCeiling` (new optional param, falls back to `advice.KvBytesPerToken` when null). The footprint overflow-GiB text uses the same effective value.

## Context fidelity (how to survive auto-compaction)

The gateway auto-compacts chat history when context nears the window limit. The compaction (`compact_openai_history_payload` in `.vscode/fluxmux.ps1`, ~line 3788) is **lossy by design**:

- Keeps the **last 8 messages** verbatim (`context_compaction_keep_turns: 8`).
- Keeps **all `system` messages** verbatim.
- Everything older is flattened into a single system summary: each old turn → `role: <first 220 chars>`, only the **last 24 such lines** survive, whole thing **hard-capped at 5000 chars**.
- **Tool results are not preserved** — only `user`/`assistant` text is summarized; tool-call payloads are dropped.

Consequences: the original brief is the first thing truncated (220 chars) and eventually dropped from the 24-line window; established decisions survive only if they're in the last-8 tail or land in the per-line summary.

**Pattern to preserve fidelity across a series of tool loops:**

1. **Externalize the brief + key facts to disk early** (this `STATUS.md` is for that). It's a file, not chat history, so compaction can't truncate it.
2. **Re-read `STATUS.md` surgically after each compact.** The summary drops tool results and old text; re-reading the file you need is the cheap way to restore fidelity.
3. **Keep the brief short and self-contained** (ideally <200 chars) so it survives the 220-char-per-line summary *and* the 24-line window.
4. **Re-anchor explicitly at decision points.** Restate the 2–3 governing constraints in your own reply (stays in the verbatim last-8 tail) even if the summary loses them.
5. **Prefer files over chat for anything you'll need later** — decisions, file paths, exact command flags, "do NOT do X" traps. The compaction layer is lossy; the filesystem is not.

The honest limitation: the summary is a fixed 5000-char / 220-char-per-line / last-24-lines window, not a faithful transcript. The only robust answer is externalization: **the brief lives in a file, and the model re-reads it after compaction.**
