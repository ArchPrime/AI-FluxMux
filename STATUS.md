## Refactor proposal: split monolithic files (this session, 10/10)

The following files are large enough to cause real problems for AI-assisted editing (context window pressure, editor tool fragility, cognitive load when tracing nesting):

**Recommended approach — surgical, per-file:**

1. **`MainWindow.axaml` (highest priority, lowest risk):** Split into per-tab `UserControl`s. Each tab (Model Profiles, Cloud Profiles, Servers, Environment, etc.) becomes its own `.axaml` + `.axaml.cs`. No logic changes — just XAML reorganization. Binding context stays `MainViewModel`. Each file drops to ~300-600 lines. Start with Model Profiles tab as proof of concept.

2. **`MainViewModel.cs` (biggest offender):** God-object. Split by feature area (local profiles, cloud profiles, gateway, updates, etc.) into partial classes or dedicated services. Bigger refactor, higher risk.

3. **`FluxMuxRuntimeService.cs` / `FluxMuxGatewayHost.cs`:** Similar story — extract feature boundaries into smaller services.

7. **Typing "retry" after a port-rule halt → very long delay (sometimes minutes); subsequent requests also delayed.**
   After a port-rule stop, the local model/llama-server state may be left half-open. On "retry" the gateway re-enters the local route and can sit in a long startup-retry / warmup-probe / circuit-breaker backoff (`LocalLoadingRetryPolicy`, `LocalLaunchStartupRetry`, `CloudCircuitBreaker`/`Retry-After`), and a stuck in-flight request blocks the single local route so later requests queue behind it. **Action:** add a fast "retry" fast-path that (a) detects the prior port-rule halt, (b) cancels any stale in-flight local request, and (c) bounds the startup-retry/backoff so a retry responds quickly or surfaces a clear "model not ready" instead of hanging for minutes.

8. **llama-server RAM leak: usage creeps up to fill all 64 GB even when FluxMux is idle; causes Windows to crash/reboot.**
   **MITIGATED (memory guard added 10/10, compiles clean, NOT DEPLOYED).**
   **Root cause (confirmed):** llama-server (not the FluxMux gateway — gateway is 0.31 GB, llama-server was 39.77 GB WS / 54.44 GB private) was launched with `--cache-ram -1` because **every profile has `LocalCacheRam=Unlimited`**. That flag means an *unbounded* RAM KV cache, so the server's RAM footprint creeps up over time (KV cache + context + offloaded tensors) and is never released while idle. With `IdleTimeoutEnabled=False`, the server never stops, so it can OOM the 64 GB machine → Windows crash/reboot.
   **Fix (defensive guard):** added a **memory guard** in `FluxMuxRuntimeService` that runs in the existing 30-second idle-timeout loop, *independent* of the idle-timeout setting. When available physical RAM drops below **4 GiB** (`MemoryGuardMinAvailableRamGiB`), it stops llama-server (via the same `StopLocalCoreAsync(preserveParkedForIdleWake: true)` path the idle-timeout uses) and posts a notice explaining why and how to reduce RAM use. A **5-minute cooldown** (`MemoryGuardCooldownMinutes`) prevents stop/restart flapping; the next chat reload re-tests the condition.
   - Files changed: `Services/FluxMuxRuntimeService.cs` (new `_lastMemoryGuardStopUtc` field, `MemoryGuardCooldownMinutes` + `MemoryGuardMinAvailableRamGiB` consts, `ConsiderMemoryGuardStopAsync` method, call at top of `ConsiderIdleUnloadAsync`).
   - **Verified:** `dotnet build FluxMux.Avalonia.csproj` → 0 `error CS`. Full test suite: 1574 pass.
   - **Deploy:** close app → `build-fluxmux.bat clean` → restart.
   - **Orphaned-process fix (10/10):** the initial guard only fired when `IsManagedLocalAlive()` was true, which requires `_localServerProcess != null`. If the app was restarted and llama-server was already running from a previous session (or the process handle was lost), `_localServerProcess` would be null and the guard would skip it — so the leak continued. Added `HasOrphanedLlamaServerProcess()` (checks `Process.GetProcessesByName("llama-server").Length > 0`) and the guard now fires when **any** llama-server is running, not just the one this instance launched. `StopLocalCoreAsync` already handles orphaned processes via `StopStaleManagedLocalFromRuntimeState` + `TryStopLocalEndpointOwnerByPort`.
   - **Root-cause fix: capped "Unlimited" RAM cache (10/10):** the real problem was that `LocalCacheRam=Unlimited` passed `--cache-ram -1` (truly unbounded) to llama-server, so the RAM KV cache could creep up to tens of GB. On a 64 GB machine that's ~38 GB — enough for the overflow context, but it can never consume the whole machine. This is the actual fix for "memory should never have got this high"; the memory guard above is the safety net if something else still runs away.

To actually reduce RAM use: (a) enable the idle timeout (Servers → Advanced) so the server stops after N idle minutes, and/or (b) set the profile's **RAM cache** to a fixed value (e.g. 8192) instead of **Unlimited**, and/or (c) lower the context size. The guard's notice message suggests these.

## Context fidelity (how to survive auto-compaction)

The gateway auto-compacts chat history when context nears the window limit. The compaction (`compact_openai_history_payload` in `.vscode/fluxmux.ps1`, ~line 3788) is **lossy by design**:

- Keeps the **last 8 messages** verbatim (`context_compaction_keep_turns: 8`).
- Keeps **all `system` messages** verbatim.
- Everything older is flattened into a single system summary: each old turn → `role: <first 220 chars>`, only the **last 24 such lines** survive, whole thing **hard-capped at 5000 chars**.
- **Tool results are not preserved** — only `user`/`assistant` text is summarized; tool-call payloads are dropped.

Consequences: the original brief is the first thing truncated (220 chars) and eventually dropped from the 24-line window; established decisions survive only if they're in the last-8 tail or land in the per-line summary.

**Pattern to preserve fidelity across a series of tool loops:**

1. **Externalize the brief + key facts to disk early** (this `STATUS.md` is for that). It's a file, not chat history, so compaction can't truncate it.
2. **Re-read `STATUS.md` surgically after each compact.** The summary drops tool results and old text; re-reading the file you need is the cheap way to restore fidelity.
3. **Keep the brief short and self-contained** (ideally <200 chars) so it survives the 220-char-per-line summary *and* the 24-line window.
4. **Re-anchor explicitly at decision points.** Restate the 2–3 governing constraints in your own reply (stays in the verbatim last-8 tail) even if the summary loses them.
5. **Prefer files over chat for anything you'll need later** — decisions, file paths, exact command flags, "do NOT do X" traps. The compaction layer is lossy; the filesystem is not.

The honest limitation: the summary is a fixed 5000-char / 220-char-per-line / last-24-lines window, not a faithful transcript. The only robust answer is externalization: **the brief lives in a file, and the model re-reads it after compaction.**
