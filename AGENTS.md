# AI-FluxMux — resume here

This folder is the Avalonia desktop app **AI-FluxMux v0.4.0**. It launches local GGUF models through **llama-server**, can route cloud models, and presents one OpenAI-compatible address to a **Client app** (Cline or Harness).

Open **this folder** as the Cursor workspace. The parent `Workspace` git tree also holds other projects; its `AGENTS.md` is a WinForms layout policy and does not apply here.

Do not restructure `MainViewModel.cs` / `FluxMuxRuntimeService.cs` / `MainWindow.axaml` for GitHub cosmetics while behaviour is still changing. Extract a slice only after that behaviour has settled (Health copy, Compact, idle timeout, fingerprints are the pattern). Decompiler leftovers in `FluxMuxRuntimeService.cs` (`goto IL_*`, `if (1 == 0)`, `num`/`text`/`flag`) have been removed — do not reintroduce them, and do not mix a further split of that file with profile, Validate, or NVFP4 launch work.

## Reasoning protocol (always in effect)

When reasoning about a non-trivial problem, lay out **(a) what you've established** (facts confirmed from the code/logs) and **(b) the unresolved dilemmas** (open decisions), then ask the user to decide — **do not cycle/re-derive the same points indefinitely.** If you find yourself re-arguing a point you already made, stop and present the established facts + the specific dilemma instead. This was requested after the agent cycled on the stress-test graph throughput question.

## Documentation (always in effect)

Every code change must be accompanied by a documentation review/update. The reasoning for a non-obvious decision must live in the repo, not only in the chat, because the chat is gone by the time the next maintainer (a stranger, or another AI, possibly long after the author) works on this code.

- **At the decision point:** when you add or change non-obvious logic, add a short comment stating the *why* (the reason / invariant / failure mode it avoids), not just the *what*. Examples of the kind of "why" that must be captured: why `.git` folder paths are normalized to their parent, why `git log --grep` needs `--fixed-strings`, why a commit message embeds the folder name, why Omit and compaction are gated off for a profile that leaves compaction to the Client app while VIBE_STATE stays on (prefix-stable, so it does not invalidate the KV cache).
- **Keep it current:** if a change alters behaviour that a doc or comment describes, update that doc/comment in the same change. Do not leave a comment that describes the old behaviour.
- **Scope:** this applies to `Services/`, `ViewModels/`, and the public docs (`AGENTS.md`, `README.md`, `*.md` specs). Trivial renames, generated files, and `.axaml` view layout do not need new prose, but a behaviour change behind them does.
- **No orphan knowledge:** if you resolve a bug or make a trade-off that is not obvious from the code alone, the resolution must be recorded (comment or doc) so it is not re-litigated or "fixed" back.

## Product facts

- Public Endpoint URL / **Port**: `http://127.0.0.1:5001` (change only if Endpoint settings use another port). That is what Client apps call. Several can be active at once (Cline and Harness together) if they all use this Port.
- **Daemon port**: private listen port for **llama-server** (usually Port+1). AI-FluxMux talks to llama-server there; do not point a Client app at it.
- Client app dropdown is extra setup notes and Harness controls, not exclusive ownership of Port and not routing-dialog naming. Cline and Harness can share Port; dialogs always cover both, and Harness web is detected when it is actually up. The Harness block on Servers (install links, web UI port, settings.yaml) follows that dropdown — shown for Harness, or whenever Harness web is actually up (`ShowHarnessServersPanel`), so a Cline operator is not asked to set a Harness port. The Quick Select launcher and its stop stay ungated (`ShowHarnessSetupPanel`); do not gate those on the dropdown, or a running web chat has no stop. `Help.html` carries that symmetry too: **Cline** and **DeepSeek Harness** are a Heading 2 topic each, linked from their subheadings under *Choosing a Client app for local models*. The Cline topic must keep saying that a new model does **not** need a new task, which is the one place the two clients genuinely differ. The Cline block is the same shape (heading, note, links, status line), but its status is `ClineContextSync.ReadPortStatus` — not found / points elsewhere / points at Port — because Cline is an editor extension with no version AI-FluxMux can read, and pointing at Port is the precondition for Launch syncing it. Do not add a per-model **launcher** for Cline to match Harness: Harness needs a new session to pick up rewritten yaml, while Cline keeps model id `local` and picks up the new model on its next message, AI-FluxMux cannot open a Cline task from outside the editor, and reaching into that webview is what raced it before. Launch runs one Endpoint-settings sync (`EndpointSettingsSync`) for every enabled adapter that already points at Port. Built-ins: `cline-4x`, `harness-yaml`. Optional `EndpointAdapters` array in `fluxmux_config.json` can disable those or add `kind: json-merge` clients (sample: `endpoint-adapters.example.json`). Servers → **Export / Import Endpoint adapters** writes Port + that array only (no secrets, no model profiles) so a bad JSON edit or a reinstall can be recovered. Model Profiles → **Export / Import model profiles** writes a temporary pack that patches live `LocalProfiles` / `CloudProfiles` only when the file is clean (no secrets, no live-config keys); same-name different settings and same-settings duplicate variants are skipped. Do not put a development config in the public zip.
- Client app: OpenAI Compatible, model id `local`, API key can be a single space. Native Cursor Chat cannot reach `127.0.0.1`. That stays out of `Help.html` on purpose: Cursor offers no OpenAI-compatible setting to fill in and says so itself, so the note only distracted a new user working through setup. Do not add it back. Cursor is not a Client app of AI-FluxMux and never appears beside Cline in Help or UI — say **VS Code** alone, and do not "correct" that to "VS Code or Cursor". AI-FluxMux never routes *to* a Client app in the first place: clients call Port, nothing is sent out to them, and Cursor never calls Port because it exposes no OpenAI-compatible setting. Cursor's only role in this project is the IDE the code is edited in.

Do not put Discover / Use Discovered Server Port back next to Port — that control copied a listen port into Port and could point the Client app at llama-server or Harness. The scan code can stay unused.

The Help tab loads the newest `Help.html` next to AI-FluxMux.exe, in the folder you started from, or in `%AppData%\AI-FluxMux\` (a Word save in this folder wins over a stale `bin\Debug` copy).

## Cline reinflate + KV-cache architecture (do not "fix" back)

Cline reinflates the **full** chat history on every turn. That single fact drives the cache strategy:

- **Exact-prefix KV cache is the goal.** llama-server's cache hits only when the prompt prefix is byte-identical to the previous turn. Anything that rewrites the forwarded prompt between turns breaks the prefix → LCP similarity drops (0.70–0.78 observed) and prefill costs 8–13 s of cache misses.
- **One per-profile choice decides who controls context compaction** (24 Nov): Model profiles → Context management → **Context compaction controlled by: AI-FluxMux, Port rules settings / AI-FluxMux, this profile's settings / The Client app** (`LocalAutoCompactMode` `port-rules` / `per-profile` / `none`). It replaced three overlapping controls: an **Auto-compact** tick box that nothing at runtime read, a Fit and memory **Compact** tick (`AutoCompressEnabled`, which only gated the Port-rules path; Launch now seeds `forward_compact` from the mode instead, and the key stays in JSON for old files), and the Diagnostics **client style: Other / Cline-like** box, which was global, forced the edited profile to None behind the operator's back and restored it only from memory. Almost every agent Client app (Cline, Harness, …) shortens its own chat, so this is a choice for any Client app, not a Cline switch. "Reinflate mode" below now means **the running profile is set to The Client app**: `FluxMuxRuntimeService.UserClientReinflatesContext` reads that live from the state file and config each call. Hail Mary no longer depends on this choice (see *Hail Mary works on the Client app's side*). Likewise the steps that read or write a Cline task's files (the Cline compaction-edge watch `ObserveClineEssenceEdge` and the Cline session key in `ObserveEssenceEdge`) also need the request to carry Cline's message ids (`RequestCarriesMessageIds`): without them the session match falls back to the most recent Cline task, so a Harness chat on "The Client app" could have rewritten an unrelated Cline task's compaction file.
- **The Client app shortens, AI-FluxMux keeps a last resort at 95 %** (`TryLastResortCompact`, `LastResortCompactShare`). With "The Client app" AI-FluxMux used to switch off *all* shortening, so a chat the client shortened too late, or one very large turn, was refused as too large and only Hail Mary could rescue it. Now it shortens with the same stepped cut once the prompt reaches 95 % of the Context. Cline's own Auto compact acts well before that, so this rarely fires. An unresolvable profile is treated the same way (no Port-rules fallback, last resort only).
- **In reinflate mode the prompt-modifying systems are gated OFF:** Session Artifacts, Tool Result Clearing (`LocalToolResultClearing`), and regular History Compaction (only the last resort above remains). This is done in `FluxMuxGatewayHost.cs`. Do not re-enable them for that choice — the Client app has said it does the shortening, and a rewrite each turn is what broke the prefix.
- **When FluxMux does compact (either AI-FluxMux choice, the default even for Cline), the cut moves in steps and the prompt cache stays on.** A reinflating client resends the whole chat, so compaction is redone every turn — that is not wasted, but a cut that slid one message per turn (`keepStart = Count − keepTurns`) changed the summary and the first kept turn on every request, so only the system prompt was reused; on top of that `LocalPrefixCachePolicy` set `cache_prompt: false` after every compact, claiming reuse after a prefix change was unsafe. It is safe: llama-server rereads from the first differing token. Now `LocalHistoryCompaction.TryCompactPayloadStable` rounds the cut down to a multiple of the keep count (tail runs from keepTurns to just under 2× it) and falls back to the tight cut when the stepped result would not fit the Context; the cache-off policy and the Port rules "skip prefix cache" tick box are gone (`SkipPrefixCacheAfterCompact` stays in JSON for old files only). Measured (`PromptPrefixStabilityTests`, 90-turn tool session): reread after compaction 55.8 % → 11.6 % of the prompt; on the RTX 5090 with a ~16K-token prompt, 5.86 s (cache off) → 0.57 s between cut moves, ~3.8 s on the one turn in eight where the cut moves. Do not go back to a one-message slide or to disabling the cache after compact.
- **Compaction cuts to a target fill, not to the keep count (26 Nov).** `LocalHistoryCompaction.TryCompactPayloadToFill` keeps as many recent messages as fit in 20 points below the share that triggered it (`FillTargetShare`: 60 % for an 80 % per-profile trigger, 65 % for the 85 % Port-rules watermark, 75 % for the 95 % last resort); Keep turns / Tool keep turns are now the minimum. The cut start is rounded up to a multiple of `FillCutStep` (32 messages), so it stays put while that many messages arrive and the prompt cache holds, as the stepped cut intended. Every fit check scales the chars / 4 estimate by this request's measured ratio (`PromptTokenRatio`: measured tokens / estimate), because the estimate is off both ways (a code-heavy agent chat measured 1.5x). After any compaction the gateway re-measures the prompt before `ShouldBlockLocalForward`: it used the pre-shortening count and refused a turn the last resort had just shortened ("blocked … n_prompt=196864"). Found by the Live-Switch test: max fidelity cut a ~197K chat to 9,282 tokens (6 % of 163,840) and lost 7 of 10 facts.
- **Compaction keeps the opening request, the person's earlier messages and values from older tool output (26 Nov).** The opening request is pinned (verbatim up to Preserved user chars) as well as the newest task; it never changes, so the prompt cache is unaffected. The summary of the dropped part now always lists the person's earlier messages (the 20 most informative, in order — they were left out whenever a tool ledger existed, i.e. in every agent chat) and "Values found in older tool output": up to three lines per result that state a value (`key = literal`, a git log line, a test or error outcome; code such as `total = sum(...)` does not match), newest first when over 40. Cap 8,000 chars (`MaxSummaryChars`). The tool ledger rule stands: no file bodies. `CompactionKeepsFactsTests` compacts the Live-Switch chat as max fidelity does and requires all ten planted facts to survive; before, four were lost (the opening codename, a config port, a ruled-out library, a flaky test).
- **Built for tasks that change direction (26 Nov).** Reviewing a long vibe-coding chat showed the task moving on many times and decisions reversed within the hour, while the brief and compaction gave the opening request pride of place and listed every note as if still true. Now: compaction's summary states `HandoverBrief.LatestWinsRule` ("Later messages override earlier ones…"), labels its notes "oldest first; later ones override earlier ones", and always keeps the newest `NewestDroppedNotes` (8) dropped messages of the person's before filling the rest by informativeness (a short "No, revert that" lost to wordy, value-heavy messages before); the pinned opening carries `OpeningLabel` ("Where this chat started. Later messages may have changed the task…"; constant, so the prompt cache is unaffected), and a pasted brief as the opening is pinned whole up to `PinnedBriefChars` 40,000 instead of being cut at Preserved user chars. The brief leads with **Where things stand now** (latest turns word for word, final message), then **How we got here** (the person's messages oldest first, one line each, repeats folded as "(and n more like it)", the middle left out over 8,000 characters, never the start or the latest), then **Facts gathered along the way** (compaction's summary without its person notes, files changed), and last **Where it started**, labelled as a starting point. A chat that began from a brief carries it forward (`EarlierBrief.Parse`): its starting point stays the starting point, its history (and its final message) open this one's under "(in the chat before this one:)", its facts lead this one's — so a task handed over several times keeps its whole trajectory instead of the earlier brief being cut at 4,000 characters. Hail Mary's rebuild summary has the same shape without "now" (the kept tail is that). Saved briefs are named after the final message, not the opening. Reversals are not detected from text ("save automatically" vs "don't" cannot be told reliably); the order and the rule hand that judgement to the model.
- **Hail Mary finds the Cline task by the chat's own opening line, not by reading the summary (26 Nov).** `HandoverBrief.OpeningProbe` takes the first line the person wrote (80 characters) from the saved chat. It used to be read back out of the rescue summary from under "## Original request"; the restructure above renamed that section, the probe came back empty, and the first live press matched no Cline task ("no recent Cline task holds the saved chat") — caught only by a live test, so keep the probe independent of summary wording. The same test showed Cline 4.x wrapping typed input as `<user_input mode="act">` (or "plan"): `ConversationText.HumanPart` now unwraps it, as it did `<task>` / `<feedback>`, so the wrapper no longer reaches compaction notes, VIBE_STATE, the brief or its file name ("… user input mode act now add a.md"). A chat without message ids is keyed by a hash of its first human message, so such a chat is seen as new once after this change. Live check (26 Nov, throwaway task "HAIL MARY TEST"): a 198K-token Cline chat in a 213,056 Context was rebuilt as summary + 29 recent messages, ~54 %, the `.compaction.json` written with Cline's source-prefix hash; On reopen Cline ignored it and resumed the whole chat: Cline applies a `.compaction.json` only when `source_prefix_hash` equals its own hash of the first `source_message_count` messages (with a hash present it never falls back to the last-message key), and Cline 4.1.27 normalises user text before hashing (`s0`: unwrap `<user_input …>` / `<user_command …>`, drop `<mode_notice>` blocks, `/slash` prefix for a whole-message `<user_command slash=…>`) where AI-FluxMux only trimmed, as older Cline did. `ClineCompactionWriter.ClineUserText` ports `s0`; `ClineCompactionHashTests` pins the hash Cline's own functions give in node on a fixture, and on the test task the rewritten file's hash matched Cline's. When a Cline update stops Hail Mary taking effect, rerun Cline's `PGo` / `JPp` / `RGo` / `s0` (in its `dist/extension.js`) on a task in node and compare before changing anything else. **Verified end to end (26 Nov):** a 10-fact Cline task of 229K tokens (over the 213,056 Context), refused for size, rebuilt by Hail Mary (176 of 319 messages summarised, 143 kept), then resumed by Cline's own core with "retry": Cline loaded the rebuild, sent 146 messages (107,688 measured tokens, 51 %), no AI-FluxMux shortening, and the model answered 10/10. Cline applies the file only when it starts a session for the task (opening it from history, or resuming), and only after the task's manifest (`<id>.json`) passes Cline's schema; a hand-written test task with a minimal manifest is silently resumed in full, which cost three misleading live runs, so build test tasks from a manifest Cline wrote. Cline also re-pairs stored messages on load (one message per tool call, tool result and model text; the person's consecutive messages merged); a test task in another shape is reshaped and its hash changes. **How to test without VS Code:** the extension ships Cline's core as `dist/plugin-runtime/node_modules/@cline/core` (Node, ESM); `ClineCore.create({ backendMode: "local" })` with `CLINE_DIR` / `CLINE_DATA_DIR` pointing at a sandbox copy of the task (and of `db/sessions.db`), `start({ config: { sessionId, providerId: "openai-compatible", modelId, apiKey, baseUrl, cwd }, initialMessages, interactive: true })` with no prompt (a prompt at start skips the compaction state), then `host.runTurn({ sessionId, prompt })` resumes it as VS Code does; point `baseUrl` at Port for a real turn, or at a stub server to see exactly what Cline would send. `parseSessionCompactionState` / `projectSessionCompactionState` check a file on its own.
- **A saved "(defaults)" profile is what launches (26 Nov).** `ResolveLocalProfile` returned only the config's top-level keys for "(defaults)", so the `<model>::(defaults)` entry that Quick Select and Model Profiles show was ignored: it showed Context 213,056 and loaded 163,840 from hardware advice (its earlier YaRN 393K values never loaded either). The saved entry is now laid over the top-level keys, and `ApplyRecommendedAutoLaunchSettings` treats a default carrying `IsModelDefault` like any saved variant (only missing / Auto values filled in). A model with no saved default keeps the pure auto defaults.
- **Omit waits until the prompt is half the loaded Context, then stubs in steps of 8** (`ClearOlderResultsWhenFilling`). The plain "keep the newest 16" moved the stub point every turn: live, prompt similarity 0.13 and ~39K tokens (~8.5 s) reread every turn; after the change, 0.95 and ~2.2K tokens (~0.8 s) on the turns between steps. Replay with Cline's `read_files` shape: 60 % → 7.2 % reread. The Mill rules do not depend on Omit (see the Mill check entry below). Omit decides before the request is measured, so "half the Context" is read through the smoothed measured-tokens / estimate ratio of earlier turns (`_smoothedPromptTokenRatio`, 70/30 smoothing so one turn cannot flip it): on a code-heavy chat the chars / 4 estimate is ~1.5x low, which made the start ~75 % of the Context (26 Nov). **Rapid-churn is removed** (retired 24 Nov, code removed 25 Nov): with cached turns at ~1 s it paused ordinary fast work, and all it alone caught was fast, varied, useful-looking calls — not a loop. Its settings, view-model fields, pause text and tests are gone; old `rapidChurn*` keys in a Port rules file are ignored (`rapidChurnEnabled` still marks a file that has per-rule toggles, for the legacy `enforceStops` read). Do not bring it back as a pace rule; a stuck chat is caught by repeats, failure runs and the Mill rules.
- **Repeated identical tool results become a pointer** (`LocalToolResultDedup`, either AI-FluxMux choice, gated with Tool result clearing). A later result whose text equals an earlier one still in full is replaced by a one-line pointer; matching is on text, so a changed file never matches. It runs **last** (just before forwarding, after Omit and every compaction path) so the copy it points at is guaranteed to be in the sent pack — do not move it earlier, or compaction can drop the copy and leave the model a pointer to nothing. Always the later copy, recomputed identically each turn, so the prompt start stays cache-stable. Measured in two long Cline tasks: repeats were 7.4 % / 3.4 % of tool-result text (upper bound; Omit stubs some first).
- **A repeated command gets a note before a pause.** From `CountRepeatedToolCommand` = 2, every repeat appends `RepeatedCommandNote(n)` to the newest message (firmer from 3), including a turn the operator sends anyway; only ≥ 3 pauses for the operator, and the pause names the count rather than claiming the model was already told (a chat can already hold 3+ repeats from before the note existed). Seen in practice: a listing whose filter excluded every file returned nothing and the model reran it unchanged ten times. A finding that says the fault is in the Client-app chat gets `SteerNoticeClientCloser`, never "raise the Port rule", which contradicted it. The note alone did not work: with seven identical attempts in the chat the model repeated an eighth time (Cline then stopped the task itself). So the forwarded pack also keeps only the first attempt of the run (`CollapseRepeatedToolRun`, gated like Omit), with the note stating the count. A message the person wrote after the run ends it (`CountRepeatedToolCommand` returns 0): they have already stepped in. Without that, a resumed chat whose kept tail ended in three repeats paused the person's own "Stop, just reply OK" to ask them to steer (26 Nov, Hail Mary test); a repeat after their message starts a new run.
- **Repeat = same call, and for normally-exempt calls the same result too.** Tests, builds, `python`, reads and anything naming a path used to be exempt outright (`IsClosedLoopFingerprint`), so a python listing run five times with identical output went unnoticed until Cline stopped the task. `RepeatRunMessages` now counts those only when the results are identical; a rerun after an edit changes the result and is not counted. A step that also made another call ends the run. "Same call" means the **whole** call — name and every argument (`ExactToolCall`) — not the short fingerprint used in logs and notes (`edit <path>`): Harness answers every successful edit with the same "has been updated successfully" line, so three different edits to one file read as one command run three times and paused the turn (24 Nov).
- **The Closed-loop mill ceiling counts tools since the person's latest message, not the whole chat** (`CountToolResultsSinceHumanMessage`; `ClosedLoopRunawayOmittedResults` keeps its JSON key and default 256). It compared the chat's total of older tool results, so any long chat reached it however productive: 25 Nov it paused a Harness chat with 272 tool calls over 10 turns, at most 60 in one turn, 6 errors, the last turn 22 different edits then a syntax and a browser check. A runaway is many calls in one go with no word from the person; whether the recent work is useful is the other Mill rules' job. Port rules readout and pause text say "since your last message".
- **Mill check counts tools since the person's latest message too, and shell reads count as reading** (25 Nov). It was "Mill at omitted" and compared `millDepth` — older tool results across the whole chat, stubbed or not — so once a chat was long, every turn was judged by the Closed-loop lookback alone, including the first tools after the person had just said what to do next. Live test: 304 older results, a fresh message, then 40 `type file.txt` reads → paused, because the lookback's "useful work" list knew read *tools* but not shell reads. Now `ShouldHaltAsToolMill` uses `CountToolResultsSinceHumanMessage` for both Mill check and the ceiling (`millDepth` and Omit's `eligible` count are gone), and `IsShellReadFingerprint` (cat/type/head/ls/dir/grep/rg/findstr, `git status|log|diff|show|blame|grep`, PowerShell equivalents; any `>`, backtick, `-exec` or `-delete` disqualifies) counts toward **varied** investigation only (`RecentToolsAreDiverseInvestigation`). It is kept out of `RecentToolsAreRepeatMill` and `RecentToolsAreFileReadInvestigation`, so the same `dir` coming back is still an echo mill. The UI label, pause text and Help row say **Mill check**; the JSON keys `millAtOmittedEnabled` / `runawayOmittedResults` and the identifiers `MillAtOmittedEnabled` / `RunawayOmittedResults` keep their names.
- **Removed: forward pruning and context paging (25 Nov).** Do not bring them back as they were. *Forward pruning* (`ForwardPrune`, per-profile "Trim waste per turn") acted only once the prompt was already over the loaded Context, i.e. after Omit had stubbed the same older results (394 turns logged that day, nothing cut); its tool-result truncation kept "the newest 8" in full, so its cut moved every turn and would cost a prompt reread each time it acted; its other two steps are covered by `LocalToolResultDedup` and `CollapseRepeatedToolRun`. Its only distinct case was Omit switched off — where it rewrote results the operator had chosen to keep. *Context paging* ("Page context (lossless spill)") swapped old results for a `swap_id` pointer to be read back with `read_swap_log` over AI-FluxMux's `POST /mcp`; that route took a custom `{"tool","args"}` body, not MCP's JSON-RPC, so no Client app could connect, the swap store had been empty since 9 Nov, and the tick box promised a lossless read-back that could not happen. `update_vibe_state` went with it (VIBE_STATE is captured automatically). The **📌 Checkpoint** button, which went through the same control plane, now calls `GitRunner.CreateCheckpoint` directly. Ideas worth rebuilding properly (gentler head+tail step inside Omit; VIBE_STATE from the Client app's own `todo_write` list) are in the local `NEXT_SESSION_PLAN.md`. Old profiles may still carry `LocalForwardPruneEnabled` / `LocalContextPagingEnabled`; nothing reads them.
- **Failed tool calls in a row get a note, never a pause** (`CountTrailingFailedToolResults` ≥ 3 → `FailedToolRunNote`). Cline (OpenAI Compatible, per its `extension.js`) sends a result as the JSON of its result list (`[{"query","result","error","success":false}]`) or `{"error":…}`; `IsFailedToolResult` reads those. Counting stops at a success or at a message the person wrote. In the operator's Cline history: 93 runs of ≥ 3 failures in a row, longest 11; Cline stops a task after six errors.
- **`forward_compact` means "Compact is on"; `compact_now` means "the operator clicked Compact".** Launch seeds `forward_compact` from the profile, and the gateway used to read that same flag as a force request: it force-compacted the first turn after every launch and then cleared the flag, which switched automatic Port-rules compaction off for the rest of the session (0 automatic compactions in the log afterwards, against 7,355 before). Only `compact_now` forces now, and only it is cleared.
- **Compaction-edge detectors ignore requests under 1,000 tokens** (`CompactionEdgeDetector.MinObservedTokens`, and the same gate in `ObserveClineEssenceEdge`). The 59-token request a Client app sends after start-up or a profile switch read as "restarted" or as Cline compacting "392 → 1 messages", and rewrote that Cline task's compaction file. `ObserveEdge` also says which edge it was; **only a real drop** rewrites Cline's compaction file — after a restart or a window change Cline still holds the whole chat.
- **The essence block goes at the end of the newest user message** (`InjectEssenceBlock`), like VIBE_STATE. In the system prompt it appeared on the turn the compaction cut moved and vanished the turn after, so every cut move cost two full rereads instead of one (live: 8.4K then 10.4K tokens; now 8.2K then ~2.9K).
- **Client apps' own compaction follows the running profile, both ways (27 Nov).** The running profile's "Context compaction controlled by" decides; nothing is hard-wired (operator's rule). Cline: `useAutoCondense` (globalState.json) and `autoCompactEnabled` (global-settings.json) are set **on** for The Client app and **off** for either AI-FluxMux choice, whatever they were, written even when missing (`ClineContextSync.ApplyAutoCompactFlag`). Harness: told the **loaded** Context under The Client app, since its own compaction acts on the Context it is told (told 262,144 with 213,056 loaded, it started too late); under an AI-FluxMux choice it is still told the largest Context a usable profile offers, so a bigger turn reaches Port and AI-FluxMux shortens first (`AdvertiseHarnessYamlContext`). Live check (27 Nov, Launch path): The Client app → Cline true / true, Harness 213,056; AI-FluxMux per-profile → false / false, 262,144.

- **Hail Mary's /smol option is removed (26 Nov).** It typed `/smol` into VS Code (`ClineSmolTrigger`, Win32 keystrokes plus a UI-Automation click on Cline's send button, because Enter does not submit a slash command) — exactly what Cline's own compact button does, under the same conditions (Cline idle), and it failed the same way on an overflowing chat; it also stole focus. ## Behaviour that is easy to break

- **Compact** only shortens forwarded history when the loaded Context is actually filling (or the prompt already exceeds it). Do not compact every turn. Compact cannot shrink a single over-full Cline turn.
- **Streamed tool calls are held until complete, then filtered whole** (`LocalToolCallHealSession`). A streamed call arrives in fragments — id and name first with empty arguments, argument text after — and the outgoing-write filter (`LocalSessionArtifactPolicy.FilterMessageToolCalls`) used to run on each fragment: "write with no path yet" was dropped, the nameless argument fragments passed, and the Client app assembled a call with no name and broken arguments. Harness failed the turn (`Tool call "": Unexpected non-whitespace character after JSON`) on almost every reply that wrote a file (24 Nov), and stored such calls are what made five Harness chats unresumable ("tool call id requires a nonempty string"). Fragments are now merged by index and sent as one piece at the choice's finish_reason (or `[DONE]`); a fully dropped reply ends with finish_reason `stop` and the dropped-writes note. Do not filter per fragment again.
- Prompt-token estimates must not treat embedded image bytes (data-URI base64) as text. Count a small per-picture allowance. A screenshot on an Images-off load is a capability miss, not a Context overflow 400.
- **Route requests** is always prompted. Cloud and local hops stay in this Client-app chat when both are already running (including Harness). A local-to-local switch that FluxMux offers reloads llama-server and is not safe in that chat — new Cline task or Harness chat. Overlay-only (temperature / max tokens) can apply without a reload, but FluxMux does not prompt a route switch for that. Offer the ready cloud only when the loaded local is already **GPU + CPU** or **CPU only** and the forwarded turn is large enough to make RAM spill worse. A GPU-only local that still fits stays local. Whenever the loaded local cannot take this turn (Context filling, RAM spill, or a capability miss) and a cloud hop is offered, hold this Client-app request for Switch to that cloud; 400 only if they keep local or the wait times out (llama-server was not asked). Closing that dialog must not steal focus from the Client app. A Load suggested local reload must not 400 that turn before the cloud hop can finish. Do not append character or token stats to those operator dialogs. Do not invent a Client app remaining-percent. After Switch to cloud, later turns the loaded local could have taken are offered back on the next capable turn. After a 400 or llama-server reload: that turn is over. Harness needs a new chat. Cline keeps model id `local` — the next message in this task can use the new model once it is ready; start a new Cline task if the same error would repeat, after a hang abort / Keep-end, or if Cline is looping a command. Live-Switch Testing probes Port after each profile is ready; it does not prove an in-flight Cline turn survives a reload.
- Harness **0.1.2+** gates the web UI with a `?token=` URL printed by `dsh web`. Opening `http://127.0.0.1:3080` without that token returns 401 (`/api/llm.providers` fails). AI-FluxMux starts `dsh` with `--no-open`, waits until that URL is in `fluxmux-harness-launch.log`, and opens it. If the UI is already up with 401 and no token is on file, **Harness web chat** restarts Harness web so the user does not have to paste a URL. Never `npm install`.
- Harness `settings.yaml` must not hide a turn FluxMux could offer a different local for. If a validated profile has Images on, Reasoning on, or a larger Context / max tokens, advertise that in yaml even when the loaded profile does not. FluxMux then offers **Load suggested** on Diagnostics / routing pop-up. Harness's own model picker is a different message. New Harness session after yaml write.
- `/v1/models` (and `/models`) is the one channel that reaches a Client app with no adapter, so it carries the **loaded** model's Context (`context_length`, `max_model_len`, `meta.n_ctx`), reply budget (`max_tokens`, `max_output_tokens`, `meta.n_predict`), and Images (`supports_images`, `supports_vision`, `meta.vision`) — several spellings because none of this is in the OpenAI spec. Reply budget is read back off the launch args (`ReadIntArg(args, "-n")`) so it is what llama-server was told, not what a profile hoped for. A capability AI-FluxMux does not know is **left out**, never asserted false: a client that is told Images are off will not offer to attach one, and that turn never reaches the routing offer. This does not replace `EndpointSettingsSync` — Cline takes Context from its own settings and defaults to 128000, Harness learns the provider exists only from `settings.yaml`, and neither Auto compact nor a base URL has a field in a models list.
- **Max tokens** is llama-server `-n` (reply budget), not VRAM. VRAM is mostly `-c` (Context) plus weights and an optional mmproj.
- **Validate** is a tiny “reply ready” probe. It does not prove a long Cline write.
- Settings-only AutoTune edits the form; **Save** keeps it, **Revert** discards it. Experimental speed AutoTune reloads llama-server. After Save, AutoTune must not lower a hand-tuned max tokens / Context / temperature / reasoning / chat template / parser / unban; it may still change GPU, batch, threads. **Images is not a wizard setting** — AutoTune works around Enable / Max image edge / projector. Images on reserves VRAM from the projector plus Max image edge (scales with edge² and leftover GPU GiB) and **may lower** a text-only Context that now exceeds the Images-on advice ceiling. When VRAM math saturates 262144, text-only Context scales leftover GiB to the known-working **213056** at ~12 GiB leftover (not 81% of 262144). Do not write 262144 as advice. Do not default an unknown GGUF to 262144.
- Overlay temperature/max tokens can apply without a llama-server reload; launch-critical fingerprint changes require Launch. Only one llama-server is loaded. A second local Quick Select slot must not show as loaded or **Hot — standing by** (that label is for a ready cloud while a local is answering). Harness `name` follows the llama-server profile that is actually running, not another variant of the same GGUF.
- Images on loads `mmproj` for the whole session (~0.9 GiB projector here) even if no picture is sent. An `mmproj*.gguf` is a vision projector, not a local model. Do not Validate or Launch it as `-m`. Pair it under Images on the matching GGUF profile.
- llama-server log lines in Diagnostics are labeled `Last llama-server output`. Verbosity is high at startup; that is not an OOM by itself. Do not write raw llama-server tails (tabs, “UI is disabled”) into the Model Profiles status row — keep those in Diagnostics.
- Launch countdown follows a **cold** llama-server load, not a **warm** cached hit, so a warm load can finish sooner. Its history (`FluxMuxRuntimeService.RecordLocalLaunchTelemetry`, eight loads per profile) lives in **`local_launch_telemetry.json`** beside the config, not in `FluxMuxMeta.LocalLaunchTelemetry`: `FluxMuxConfigService.Save()` rewrites the whole config from the window's start-up copy, so history written there was reverted by the next settings save and the countdown never followed recent loads (24 Nov: loads of 11-16 s all day, history still from 27 Oct). The old key is copied into the new file once and then ignored. A load is recorded once, by the launch itself; the window used to record it a second time, so the eight-sample window held four loads. Do not write runtime data into the main config — `last_launched_local.json` exists for the same reason.
- **Make New Variant** needs a name in the box beside the button. An empty click shows **Name your variant first**. Creating a local model profile must stay on that new row; do not leave the previous expander selected.
- FluxMux launches `llama-server.exe` only. Leftover zip CLIs (`llama-qwen2vl-cli.exe`, `llama-llava-cli.exe`, and similar) can trip Windows Defender `Wacatac.C!ml`. That is a known false positive. Exclude `C:\AI_Workbench\llama-server`, not all of `C:\AI_Workbench`. Do not turn Defender off.

## Profile editor: which launch flags are exposed

`BuildLocalServerArgs` honours about 70 profile keys, but the editor deliberately shows only those that help a local-model user; page space is limited. The rest stay **JSON-only on purpose** — do not add them to the page without a concrete need.

- **Exposed (Nov 2026):** *Draft length* (`LocalSpecDraftNMax`, beside Multi-user in *Prompt and CPU*; greyed unless Speculative is `draft-mtp`), *Thinking budget* (`LocalReasoningBudget`, second row of *Chat format*), and a collapsed **Sampling · needs a reload** group (`LocalTopK`, `LocalTopP`, `LocalMinP`, `LocalPresencePenalty`). Label values (`Auto`, `Unlimited`, `Server default`) are saved as-is and read by the launch code as "flag off", so llama-server keeps its own default.
- **Zero is a real value** for min-p (Qwen recommends 0; llama-server's default is 0.05) and for the thinking budget (0 = no thinking). Their launch code therefore does not use `GetProfileInt`/`> 0` checks, which read 0 as "unset". Do not "simplify" them back.
- **JSON-only, and why:** context shift (silently drops tokens → breaks Cline's exact-prefix cache), process priority (realtime starves Windows), CPU mask/range, LoRA path and chat-template kwargs (free text that can stop the load), web UI (invites pointing a Client app at llama-server), Jinja (covered by Chat parser), image max tokens (derived from Max image edge), context checkpoints (covered by Cache strategy), CPU MoE (handled by `--fit`), prompt cache (must stay on), preserve reasoning (can change the prefix between turns), plus low-value housekeeping: HTTP threads, timeout, warmup, metrics, load mode, draft K/V type, image min tokens, repeat last-n / repeat / frequency penalty, reasoning effort.
- All exposed keys are in `LocalLaunchFingerprint` (they need a relaunch) and `ProfileSettingsFingerprint`.

**Speed AutoTune scores generation speed.** Each trial is timed with `TimeLocalGenerationSpeedAsync`: a fixed ~256-token coding reply, scored by llama-server's `timings.predicted_per_second`. The old 16-token "ready" probe measured mostly start-up time and could not see speculative decoding — on this PC MTP is 71 → 135 tok/s (draft 2) → 152 tok/s (draft 3), yet the short probe barely moved. A trial must beat the usual settings by ≥3% (`MeaningfulSpeedGainFraction`; run-to-run noise was about ±1%) or the usual settings are kept. For a `draft-mtp` profile AutoTune tries draft lengths 2/3/4 instead of swapping to `ngram-simple`; an ngram profile on an MTP-capable model gets a `draft-mtp` trial; a profile set to **Disabled** is never touched. Validate still uses the short probe — it checks readiness, not speed.

**Micro-batch = Batch size, capped at 1024** (`LocalPrioritySettingsCalculator.DeriveUbatch`, `MaxUbatch`, and the hardware advice in `FluxMuxRuntimeService`). It used to be batch ÷ 4, so the usual Batch 1024 gave Micro-batch 256. Measured 23 Nov 2026 on this PC (27B NVFP4 MTP, Images on, Context 163840, ~16.7K-token prompt): prompt reading ub256 3,937 tok/s → ub512 5,196 → ub1024 5,577 → ub2048 5,557; b2048/ub1024 5,625. Generation stayed ~131 tok/s throughout, ub1024 costs +0.7 GiB VRAM, and chat replies at ub1024 matched ub256 (identical short answer; a long answer drifts only after the first ~850 characters, as any arithmetic-order change does). Speed AutoTune therefore has **no Batch-size trial**: it was scored by generation speed, which batch size does not move. Smaller cards than 32 GB are untested; Fit VRAM still shrinks Context if the compute buffer does not fit. Cache RAM was not changed: "Unlimited" (38,912 MiB here) is only an upper bound on the prompt cache, and there is no measurement yet showing it causes paging.

**AutoTune never picks the speculative method from the priority order.** `LocalPrioritySettingsCalculator` used to turn MTP off when Fidelity was first and swap it for `ngram-simple` when Stability was first. Speculative decoding is lossless, so that bought nothing and halved speed; it is how two variants ended up Disabled. The preset now keeps the form's current choice (`ResolvePresetSpecType`), falling back to the model-name guess only when nothing is set.

**Speed AutoTune leaves its result unsaved, like any other edit.** Each trial must be written to the profile so llama-server can reload with it. When the trials end, AutoTune reloads with the winner if the last trial was not it, then puts the pre-AutoTune profile back (`RestoreSavedLocalVariantSettings`) and leaves the winner in the form. **Save profile** keeps it; **Revert changes** really restores the old settings. Previously the winner was saved automatically (Revert could not undo AutoTune) and llama-server was left on the last trial. A variant with no saved copy yet still has the winner saved, since there is nothing to go back to.

When AutoTune puts the pre-AutoTune profile back it keeps the **current** `EndpointValidatedUtc` / `EndpointWarning` (`CarryCurrentValidationState`): the trial reloads re-validated the profile, and restoring the old stamp revived a stale ⚠ or erased a fresh validation.

**Quick Select ⚠ is a snapshot.** `ValidatedQuickSelectProfileOption.ShowMissingFileWarning` is fixed when the option list is built, so anything that changes a profile's validation state must call `RefreshProfileWarningSurfaces()` (tree, Quick Select and benchmark lists), not just `RefreshProfileEndpointStatusSurfaces()` (tree only). A successful launch now does, via `RefreshLocalProfilePresentationAfterRuntimeChange`; before, the running, validated profile kept a stale ⚠ in its Quick Select slot.

**AutoTune names what it changed, using the page's labels.** Both modes end with "Changed in the detailed settings (not saved yet): Draft length 3 → 4; KV key q4_0 → q8_0 …", built by `BuildLabelledChangeList` from `LocalDetailedSettingLabels` by comparing the form before and after. Trial names use the same labels ("Draft length 4", "Batch size 2048"). Keep that label table in step with `MainWindow.axaml` when a control's label changes; an operator could not match the old wording ("usual AutoTune settings") to any control.

## Priority list ↔ detailed settings (two-way sync)

The goal is that the priority list and the detailed settings always describe each other, so an operator gets an intuitive feel for the consequence of a manual change. Contradictions only arise from manual edits, so there are no separate "profile checks".

- **Priorities → settings:** the arrows and AutoTune write the settings (unchanged), leaving hand-set reply settings alone.
- **Settings → priorities (live):** every manual edit re-scores the settings (`ComputeLocalPriorityScores`) and moves the list when the settings clearly favour another order (`ShouldAdoptInferredPriorityOrder`, margin 3, so small tweaks do not make it jump). The info line says what changed, what it trades and how the list moved (`BuildManualChangeConsequence`, page labels, `LocalSettingTradeOffs`). A snapshot taken when the form finishes loading and after every wizard write (`RememberLocalDetailedSnapshot`) is what each edit is compared with; wizard writes never trigger re-scoring, so the two cannot loop.
- **Scorer additions:** Extend into RAM (+Context, −Speed), Context beyond the native window, Micro-batch, Draft length, Thinking budget. **Speculative Disabled no longer scores +Fidelity** — speculative decoding is lossless; draft-mtp scores as Speed.
- **KV q8_0 floor follows the order** (`KvMinimumApplies`: only when Fidelity ranks above Context length), in the calculator, `ApplyCanonicalLocalPrioritySettings` and `ReconcileLocalSettingsWithPriorityOrder`. Lower-precision KV is a legitimate choice when maximum Context matters more than Fidelity; the tooltips describe it as a trade-off, not a rule.
