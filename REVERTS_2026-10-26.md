# Reverted 10/26 Changes — `FluxMuxGatewayHost.cs`

> **STATUS: UNPROVEN.** These reverts are a *hypothesis* for fixing the "VRAM-only → YaRN switch
> won't engage / times out" regression. They are NOT confirmed to be the root cause. They restore
> the exact 10/24 behavior (which the user confirmed "used to work in seconds"), but we have not yet
> deployed and observed the fix in the running app. Treat every claim below as "we think this is what
> broke it" until a post-deploy test proves otherwise.

## Why these reverts exist

User report (10/26): switching from a VRAM-only context variant to the YaRN extended-context variant
of the same model makes the next chat turn hang / "time out." The user confirmed this exact sequence
(full VRAM context picked up by a YaRN model after a moderate delay) **used to work fine** before the
10/26 build. Diffing the current `FluxMuxGatewayHost.cs` against every 10/24 backup
(`0.3.2_0943/0947/1717/2245`) shows three 10/26 additions in the local forward path that did not exist
on 10/24. All three are reverted below.

## What was reverted (3 blocks)

### 1. Rejoin-aware proactive prune (`_firstForwardAfterStartup`) — NEW in 10/26, fully removed

- **What it was:** A field `private bool _firstForwardAfterStartup = true;` (line 52) plus a ~50-line
  block in the forward path (old lines 534–585) that ran on the **first non-probe forward after the
  gateway process started**. If that forward's prompt was ≥ 50% of `local_context`, it called
  `HailMaryCompaction.Salvage(payload, hotContext, headroom, allowMiddleCut: false, stripImages: false)`
  to proactively prune the rejoin history (stages 1–4: dedupe, loop-collapse, result-truncate,
  image-strip), and if it saved tokens it set `compactApplied = true` and ran
  `LocalChatTemplateGuard.EnsureUserQuery(payload)`.
- **Intent (as written in the code comment):** when Cline rejoins a chat after a FluxMux restart, it
  re-sends the full conversation history; this prunes it proactively so the operator "starts with a
  shorter, cleaner history instead of a packed one."
- **Why it's a suspect for THIS bug:** it is the only new code in the forward path that runs on the
  *first* forward after a (re)start. If `_firstForwardAfterStartup` was still `true` when the user
  launched YaRN and sent the first chat, `Salvage` would have run on that prompt. The user reports even
  a *new* chat hangs — and this is the one new block that touches the first forward.
- **What was removed:** the field declaration (line 52) and the entire `if (!isProbeRequest &&
  !compactApplied && _firstForwardAfterStartup) { ... } else if (!isProbeRequest) { ... }` block
  (old lines 534–585). The forward path now goes straight from
  `var compactApplied = ... TryApplyForwardCompact(...)` to
  `OfferDocumentContextDialogIfNeeded(...)`.
- **Confirmed absent in 10/24:** `grep _firstForwardAfterStartup|rejoin` on the 10/24 backup returns
  nothing. This feature did not exist on 10/24.
- **Test impact:** none. No test references `_firstForwardAfterStartup` or a "rejoin" code path. The
  only hit is a *comment* in `HailMaryCompactionTests.cs:258` ("Automatic path (rejoin prune / compact
  fallback): stripImages=false") — that test calls `Salvage` directly, which still exists and is
  unchanged.
- **UNPROVEN:** we have not confirmed `Salvage` actually hangs on a large prompt. `Salvage` is pure
  in-memory manipulation (no I/O, no locks, no sleeps), so a hang there is not obvious. This revert is
  a "remove the new first-forward code" bet, not a proven fix.
### 2. Auto-compact trigger capped at VRAM-resident context — NEW in 10/26, removed

- **What it was:** when `local_extend_context_into_ram` was true, the forward-compact trigger
  percentage was forced down to `local_vram_context` instead of `triggerPercent` of the full
  `local_context` (YaRN) window. Concretely, on the YaRN profile (`local_context` = 393K,
  `local_vram_context` = 163840), a ~236K prompt now crossed the (lowered) trigger and entered
  `TryApplyForwardCompact`.
- **Why it's a suspect:** the ~236K prompt is one big over-full turn (tool-pair-locked), so
  `TryCompactPayload` bails ("too few turns, or one over-full turn") and the Hail Mary prune saves 0
  tokens (log: "rear-context prune could not drop any turns"). The prompt is then forwarded
  **uncompacted** to the RAM-spilled YaRN model → ~236K prefill from RAM → exceeds the 600s long-load
  first-byte deadline → `request_timeout`. Before this 10/26 change, the prompt was forwarded as-is and
  prefilled in seconds.
- **What was removed:** the `if (extendIntoRam) trigger = min(trigger, local_vram_context)` (or
  equivalent) cap in the compact-trigger computation (~old line 2297). The trigger is back to
  `triggerPercent` of the full `local_context` window.
- **Confirmed:** the 10/24 backup has only two `local_vram_context` uses (lines 2357, 2503) — both
  legitimate (spill-compact dialog offer + dominant-document detection). The current file also has
  exactly two (lines 2368, 2514), matching the 10/24 baseline. The cap block is gone.
- **Test impact:** none. No test references a VRAM-cap compact trigger.
- **UNPROVEN:** we have not re-measured the post-revert forward on the live YaRN profile to confirm the
  ~236K prompt now prefills in seconds instead of timing out.

### 3. Port-rules `filling=true` forced at the VRAM boundary — NEW in 10/26, removed

- **What it was:** the same `local_extend_context_into_ram` condition also forced `filling = true` in
  the port-rules logic when `promptTokens >= local_vram_context`, independent of the actual
  `PromptFillsLocalContextForCompact` evaluation.
- **Why it's a suspect:** same root cause as #2 — it made the gateway treat a ~236K prompt on the YaRN
  profile as "filling" at the (lower) VRAM boundary, which fed the same futile-compact path that ended
  in a 600s prefill timeout.
- **What was removed:** the `if (extendIntoRam && promptTokens >= local_vram_context) filling = true;`
  line (~old line 2339). `filling` is back to being derived from
  `PromptFillsLocalContextForCompact` only.
- **Confirmed:** same as #2 — only the two legitimate `local_vram_context` uses remain, matching 10/24.
- **Test impact:** none.
- **UNPROVEN:** same as #2.

## What was NOT touched

- `HailMaryCompaction.Salvage` and `HailMaryCompaction.RearContextPrune` — both still present and
  unchanged. `Salvage` is still called by the regular forward-compact path; `RearContextPrune` is still
  called by the Hail Mary button (a separate 10/26 change, `ConsumeHailMaryMiddleCut` now returning
  `(Stop, StripImages)`). The Hail Mary button change was **not** reverted — it only fires on an
  explicit button click and cannot block a normal chat.
- The `--cache-ram` "Unlimited" cap (in `FluxMuxRuntimeService.cs`) — confirmed unchanged since 10/24
  (no diff), so it is not part of this regression.
- The launch path in `FluxMuxRuntimeService.cs` — confirmed unchanged since 10/24 (only Hail Mary +
  GPU-process display changes in the diff).
